# 组会内容总结

## 1. 先检查 CodeSecEval Python 测试文件

首先检查最原始的 CodeSecEval Base 和 Plus Python 数据集，重点看 `Test`、`Test-FP` 和 `Test-SP` 中是否存在缩进、引号、换行或代码块结构问题。

需要确认两件事：

1. 测试脚本本身能否被 Python 正确解析；
2. 测试脚本能否真正运行，而不是因为测试文件格式错误导致候选代码被判失败。

这一步针对的是 `SecEvoBasePlus/Base/Python_Base.json` 和 `SecEvoBasePlus/Plus/Python_Plus.json`，不是 PLT 数据集。原始文件必须保留，任何修复都要有单独的修复版本和修改记录。

## 2. 统计 PLT 数据集的类别、CWE 和变体

需要系统整理 PLT 数据集：

- 一共有多少条任务；
- 包含哪些 CWE；
- 每个 CWE 有多少条任务；
- 每个 CWE 内部又有哪些任务语义、函数类型和安全策略；
- 这些任务变体是如何产生或组织的。

重点是理解 PLT 中的 Seed Family。任务 ID 不同，不代表任务一定独立；几个任务可能只是同一种漏洞模式或同一个代码骨架的不同变体。

因此，`D_init`、`D_grow` 和 `D_gate` 的划分不能只按单条记录随机拆分，而应先识别 Seed Family，再按 family 划分，防止高度相似的变体同时出现在训练和门控数据中。

如果 CWE-022 的三个变体属于三个不同的 Seed Family，可以分别放到三个集合中。如果它们属于同一个 Seed Family，就必须放在同一个集合中，不能为了凑三等份而拆开。

## 3. 让经验形成过程更加可信

目前的流程是：

```text
D_init → M0 → D_grow 生成候选经验 → D_gate 门控 → M* → 最终评测
```

需要重新思考三个问题：

1. 初始安全经验学习是否也应该生成代码并运行测试，而不只是抽取文字规则；
2. R1 的候选经验生成和 D_gate 的门控之间是否存在重复；
3. 是否可以把经验生成、验证和门控组成一个更清楚的验证驱动循环。

初步方向是：R0 也加入动态验证；R1 和门控在流程上可以合并为“验证驱动经验进化”，但 D_grow 和 D_gate 的数据仍要保持独立，不能让候选经验在产生它的任务上自证。

还需要参考更多自进化 Agent 研究，明确经验如何产生、如何被验证、如何被修订或淘汰。

## 4. 尝试用人类学习安全知识的方式理解整体流程

可以把 SCT 理解为模拟人类学习不安全代码的过程：

```text
先学习安全规则和教材
→ 阅读漏洞与修复案例
→ 遇到新问题时检索相似案例
→ 编写修复代码
→ 测试和检查修复结果
→ 总结可复用经验
→ 在后续案例中继续验证和修正经验
```

这个角度可以帮助我们重新设计经验卡片、检索器和经验更新规则，让系统学习的是“什么条件下应该使用什么安全原则”，而不是简单复制过去的代码。

## 5. 突出多语言研究主题

目前多语言主要体现在数据集有 Python、Go、C++ 等版本，但 SCT 的经验学习、检索和门控基本还是按单语言描述的。

后续实验需要回答：

- Python 学到的安全原则能否迁移到 Go 或 C++；
- 语言无关的安全原则和语言特定的 API 提示各自起什么作用；
- 同一种漏洞在不同语言中是否需要不同的经验表达；
- 目标语言 harness 和编译器反馈是否能帮助经验进化。

## 6. 确定检索器的方案

从 `D_init` 到 `D_grow`、`D_gate` 以及最终生成，都可能需要检索器。检索的方向是：

```text
当前问题 → 相关安全经验
```

需要决定：

- 先使用现成的 embedding 模型，还是自己训练；
- 检索是否只依据 CWE，还是同时考虑任务语义、输入来源、敏感操作和目标语言；
- 检索器是否也需要遵守 D_init、D_grow、D_gate 的数据隔离。

当前倾向是先使用预训练的多语言 embedding 做稳定基线，再根据 D_init 的规模决定是否训练轻量检索器。
