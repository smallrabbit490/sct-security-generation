# H50三组消费方式对照如何运行？

S4的完整批次入口已接好，固定50题、19个真实近邻组、P0/P1/P2三条件、两次独立重复，共300个代码单元。11项专项封网测试通过，正式生成仍为0/300；当前只等待本批预算批准。

## 三组具体改变什么？

|条件|改变|保持|
|---|---|---|
|P0|沿用原流程|原卡呈现、采用、规划、生成及一次修复|
|P1|把原可见卡字段按条件、指导、解释等分组|字段内容、卡片编号、顺序、检索文本和调用数|
|P2|加入已经冻结的规划与代码核对提示|卡片内容、首次分析、采用格式和调用数|

同一道题的同一次重复共用首次初析和原生选卡，随后三组独立复析、规划、生成。需要修复时，各组按自己的代码与原可回流反馈重新检索，最多修复一次。第二次重复重新调用模型，Embedding仅按完全相同文本复用缓存。Q和经验库正文不更新。

H50名单和方法规则继续使用已批准的冻结版本；来源/开发/留出分别为50题、18/19/19近邻组。S4不会借本次新诊断改写P2提示或重新挑选H50。

## 预算与运行边界是什么？

拟设累计占用硬上限4500万Token、13000次物理HTTP，其中向量HTTP最多4800次。Token上限沿用既有P7每代码单元15万的工程额度；HTTP额度保留恢复容量。该数值是支出上限，实际已知与未知用量另列。

若全部代码都进入一次修复，逻辑模型调用最多2600次：共享首次初析100、共享首次选卡100、首次复析/规划/生成900、修复初析300、修复选卡300、修复复析/规划/生成900。实际流程在首次Joint通过后结束该单元。

运行器在每个缺失请求边界只派发一次模型HTTP。断连后保存失败及未知用量，停止新增派发，先核查journal/wire及成功响应，再用零API探针确认缺失边界。未决请求不自动补发，正常低成绩不重跑。累计预算不因接续新段重置。

工作日北京时间09:00—12:00、14:00—18:00不派发新模型和向量请求，已有worker在请求边界等待。最多4个worker；其他CLE实验活跃时本包不抢占运行。文件互斥和真实进程检查阻止重复实例，旧守护与排队全量保持关闭。

## 完成后怎样分析？

生成齐后自动调用原生零API回放，再完成数值分析。原生回放凭据绑定实际完成记录、冻结输入和来源段；完成记录改动后凭据失效。已生成齐的接续只补回放和分析，不再创建付费生成段。

主要比较为最终Joint的P1−P0、P2−P0，采用Holm两项校正和实际近邻组聚类区间。首次Joint、功能、安全、救回、损失、重复波动、修复次数、首次选卡一致性及声明采用变化分别列出。已测失败、正常模型生成失败、验证未测量和仍缺单元分开统计。缺测不计作已测失败。

费用读取各段真实wire请求与保存返回，不把各段累计账本再次相加，也不把行内复用用量累加。按模型及可核实的共享/条件归属分列；相同提示无法唯一归属时记为归属未知。用量未知继续保留原预留，金额等待真实价格依据。

Joint或采用有差异的配对进入实际案例队列。当前Agent须阅读题面、卡、计划、首次与修复代码及原验证证据，登记所有已读代码和原因；字段统计不能代替原因签署。模型测量与案例分析未完成前，不报告新方法提分。
