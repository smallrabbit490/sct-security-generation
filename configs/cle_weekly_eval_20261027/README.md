# FQ_RETEST 全量冻结回测

本包落实“先完整积累反馈，再检验同题收益”的要求。独立于正在运行的学习源码和输入，固定D_grow全部273题、五条件、各两次重复，共2730个P7代码实验单元。Q1是相似度排序呈现后由原LLM终选；Q2-K0至K3是相似度加冻结Q重排后由相同LLM终选。共同阈值δ=-1、λ=0.5，原P7最多三卡、一次修复、首次Joint早停、交付末次代码。

## 运行状态与命令

在项目根目录使用`translation_work/temp/cle_memory_q_env/Scripts/python.exe -B -X utf8 -m configs.cle_weekly_eval_20261027.retest prepare`做零API准备。实际输入保存在E盘运行根`FQ_RETEST/inputs`。`retest check`查看依赖和离线验证。当前接线已完成，真实回测尚未启动；必须等K0至K3完整学习、各阶段原生回放及分析完成后才能放行。

满足依赖并在允许时段后运行`retest launch`，它启动隐藏进程。`retest run`为实际执行入口；已经存在进程时不要另开实例。最多四个“题目×重复”组并行，每组五条件顺序执行，共用该组首次初析。两次重复分别请求初析和代码。每次模型和Embedding物理派发仍受既有时段与累计预算限制。

中断后先检查实际进程、`FQ_RETEST/execution_index.json`、各段state、journal和wire。只有已返回响应与完成格可精确对应，且没有未决HTTP时，才运行`retest resume`建立新段。已完成格不重新请求；同一路径的题面、排程、协议或Q文件内容改变时拒绝混跑。不得改变旧请求或重置预算。完成后运行`retest replay`零API原生回放；已有回放结果直接复用。

## 对照与冻结

每组首次查询核对query_hash、候选ID集合、余弦和卡正文标识相同，只允许呈现顺序及最终选入不同。修复查询使用本条件的代码与原P7许可反馈，因此不强迫修复候选一致。共同候选已出现差异时，即使五格都保存，也不能靠恢复跳过该差异。冻结评价不调用Q更新函数，运行前后核对全部卡的Q、反馈次数、正文和生命周期。

既有v3.2代码、旧Q迁移代码和学习期代码抵扣本包0个单元；精确相同文本/模型的向量缓存可以复用。同一题同一重复共享初析，但不同重复不得使用一次返回充当独立重复。
