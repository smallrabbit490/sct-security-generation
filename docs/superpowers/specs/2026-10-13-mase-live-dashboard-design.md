# MASE 实时运行审阅页与决策模型配置

## 目标

把 MASE 网页从只读的事后结果页补成运行中也能核查的实验面板。页面同时呈现运行状态与流程总览，并允许人工请求暂停或继续。逐题详情应能回答：模型看到了什么公开信息、各模型节点返回了什么、候选如何比较、为什么选择该候选、公开检查和官方评分分别得到了什么结果。

本设计承接用户已确认的 C 方案：运行状态与流程总览并列；暂停边界为当前任务完成并保存后暂停。实验产物继续写入 `translation_work/`。

## 页面组成

首屏左右并列两个区域。运行区展示运行/版本、明确状态、已保存任务数、完整测量数、Joint 数及其分母、待开始数、当前执行任务、当前节点、队列数、最近心跳时间、累计模型请求/失败请求和配置的并发上限。流程区展示实际架构图、节点状态和连线；尚未执行的节点与已完成、失败、跳过、运行中的节点使用不同状态。

页面下方保留逐题表格、版本比较与总体指标。选择一题后按时间顺序展示节点输入引用、模型角色和模型标识、脱敏的模型可见消息/回复、公开检查用例与结果、候选代码及哈希、选择依据、修复分支、最终代码摘要、功能/安全/Joint 评分、缺测原因和异常。隐藏测试输入、密钥、原始凭据和模型私有推理不展示；若服务商只提供原始响应，保存并显示可审计的用户/助手消息，不把隐藏推理链当作可用证据。

状态术语用直白中文区分：准备中、运行中、暂停请求中、已暂停、已完成、失败、长时间无新记录。状态推断同时依据运行元数据、版本状态、heartbeat 和事件时间；超出阈值只能标“长时间无新记录/疑似停滞”，不可据此宣称进程已退出。结果数字始终显示分母；未测量、任务未开始、进行中分别计数，不折算为失败或通过。

## 运行控制

网页提供“请求暂停”和“继续”按钮。暂停是协作式控制：服务写入该运行的控制状态；runner 停止派发新任务，等待已开始任务完成、评分并原子保存结果后，记录 `paused` 状态退出当前调度段。继续从相同签名和已保存行续跑，跳过已完成任务。重复点击应幂等；正在暂停时显示暂停请求中；完成或失败的运行不能继续。

网页不得直接杀进程，不得重写正在执行的配置，不得将“按钮已点”显示成“已经暂停”。控制接口只允许本机使用；校验 run/version 标识和状态迁移；状态文件写入需原子替换。旧版 runner 或外部导入的历史运行没有控制能力时，页面明确显示只读和原因，不呈现会误导人的可用按钮。

## 进度与事件记录

runner 维护原子更新的 heartbeat，至少写入 UTC 时间、运行与版本 ID、整体状态、计划/已保存/完整测量/待开始数量、活动任务 ID、活动节点 ID、排队数量、完成节点数、失败节点数和请求计数。节点开始和结束都追加结构化事件；事件包括任务/尝试/节点、操作类型、状态、开始/结束时间、输入引用、模型角色与模型名、请求成功/失败、使用量（未知时为 null）以及脱敏的可审阅消息摘要。代码内容可以留在现有受控逐题证据里，事件以哈希引用避免重复膨胀。

任务行仅在工作流正常结束且该题结果已持久化后计入“已保存”；官方评分只在工作流完成后运行。写入失败、API 错误、工作流未完成、评分缺测分别保留结构化原因。事件用于显示当前活动节点；heartbeat 用于总进度与停滞判断。轮询只读取新增或变化的记录，不能每次重扫并重算全部历史文件。

对于已经启动的 `mase-architecture-60-v4-20261013`，其进程启动时固定了 8 个 worker，且当时的 runner 没有暂停控制和节点开始事件。网页可以读取已保存 heartbeat/事件，并注明活动状态精度受旧记录限制；不能动态把该进程改为 40–50 并发，也不能声称暂停按钮能控制它。不得为了提速终止或破坏该运行。

## 并发与模型角色

把并发拆成两个显式设置：同时执行的独立任务数（worker）和同时在途的模型 API 请求数（全局 semaphore）。探索运行允许配置 40–50 的请求并发；建议默认目标 48，任务 worker 可单独配置且不超过运行环境可承受范围。所有角色共用全局请求闸门，避免每题多节点并行导致总请求数乘倍失控。限流/超时采用有上限的退避重试并留下请求失败事件；并发参数、实际峰值和提供方响应必须写入 metadata。达到 API 限流时不得静默降低并发或删除失败记录。

高能力模型用于具有关键判断职责的模型调用：架构设计员提出新图、记忆适用性判断、公开证据下的候选选择，以及图内其他会决定分支/方案取舍的模型节点。每个调用记录 `role -> provider/model`。逐题代码生成模型作为独立角色配置，不因决策模型升级而自动更换。版本是否晋级继续由已记录的训练集配对指标和安全退步规则确定，不交给模型主观投票。

GPT-6.1-sol 是用户提出的高能力模型示例。实现前需核实当前 API provider 是否真实支持该模型及其鉴权/并发限制。模型名不可只因字符串可填就当作可调用；预检失败应清楚报错，不静默回退到较弱模型。若只能通过另一种已配置的模型入口调用，应为关键决策角色单独配置 provider、model、timeout、retry 与 concurrency，而不把 Codex 内部模型标识伪装成 ChatAnywhere 模型。

## 服务与数据边界

仪表板继续只通过白名单 API 访问其配置的运行根，不允许任意文件路径读取。GET 接口读取状态、图、事件和任务详情；控制使用独立的本机 POST 接口并校验允许的状态转移。所有用户可见消息先脱敏；API key、环境快照、隐藏评测输入、训练源修复代码之外的敏感秘密不得进入页面事件。逐题证据中的训练示例仍须保留来源 family、来源质量和目标隔离审计。

## 验收条件

1. 运行页在数据变化后自动更新状态、运行进度、活动任务/节点、队列和最后更新时间，并把未知值显示为未知。
2. 暂停请求后不再派发新题；已开始题完成并持久化后状态才变为已暂停；继续可从已有行恢复且不产生重复任务行。
3. 节点状态图与落盘事件一致；进行中的节点可见，历史运行没有开始事件时明确显示精度受限。
4. 逐题查看能区分模型可见消息、公开检查证据、候选选择理由、官方结果和未测量原因。
5. 全局请求并发上限可设到 40–50，并在 metadata 与页面展示请求并发上限、实际峰值、限流/失败数；worker 数不冒充 API 并发数。
6. 关键决策模型与代码生成模型可分别配置和审计；不支持 GPT-6.1-sol 时预检明确失败，不自动静默换模。
7. 未完成 workflow 不进入官方评分；用户点击暂停不能被页面误报为已经暂停。
8. 对旧运行、损坏事件、缺测任务、API 错误及页面刷新/服务重启有测试覆盖；本地网页在桌面与窄屏布局验证可读、无重叠。

## 实施范围与顺序

先实现可审计的运行控制和结构化心跳/节点事件，再扩展只读/控制 API，最后补齐前端实时视图、任务详情和浏览器验证。API 并发配置与模型角色路由作为同一轮 runner 改造的一部分；当前已运行的 8 并发进程保持不变，后续安全续跑或新运行才使用新配置。独立确认集和实验结果解释不属于本次网页与调度实现。
