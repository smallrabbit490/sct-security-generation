# 运行效率优化：已完成项与待做项

> 生成时间：2026-09-20
> 背景：全量 v2 跑了 8 小时才到轮2，用户要求提高并发、去掉 Level 4、扩大 Phase2 选择面

---

## 一、已完成（本次改动，已测试验证）

### 1. Phase1/Phase2 并发 5 → 24

| 项 | 改动 |
|---|---|
| CLI 默认 | `--workers` 4 → **24** |
| 依据 | LLM 调用是网络等待型，实测 **CPU 占用仅 0.25%**（66s CPU / 7.5 小时墙钟） |
| 预期 | Phase1 5.2 小时 → **约 1.1 小时** |

### 2. Phase3 审计并发（原先完全串行！）

**这是最被忽视的瓶颈**：`phase3_audit` 原先是一个**串行 for 循环**，
每条经验要跑（基线 + 加候选）两轮完整生成 —— 轮1 审 24 条用了 **105 分钟**。

| 项 | 改动 |
|---|---|
| 新增参数 | `--phase3-workers`，默认 **8** |
| 实现 | 抽出 `_audit_one()` 作为并发工作单元；`phase3_audit` 用 `_map` 并发调度 |
| 线程安全 | 工作单元**只读**树/检索器；所有状态写入（status/absorb_or_new/records）仍在主线程串行收尾 |
| 测试 | 4 个（并发与串行结果一致、单条异常不拖垮整批、终态写入正确、参数夹取） |

### 3. 关闭 Level 4 四语言叶生成

| 项 | 改动 |
|---|---|
| 新增消融组 | **A7**（L2/3 合并 + 不生成 L4），设为默认 |
| 保留代码 | `level4.py` 与注入逻辑**完全保留**，需要时用 `--ablation A4/A5/A6` 复现 |
| 验证 | 实测带 L4 叶的任务 **0/6** ✅ |
| 收益 | 每个 seed 少 4 次 LLM 调用（约占总耗时 10~15%） |

### 4. Phase2 候选窗口扩大

**问题**：调度管线是 `273 条 → batch_size(24) → LLM 筛选 → replay_limit(96)`。
LLM **只能看到 24 个候选**，所以永远选不出更多。

| 项 | 改动 |
|---|---|
| `--batch-size` | 24 → **96**（送进 LLM 的候选数） |
| 依据 | 用户指出"池子里近 300 条，每轮只选一点不对" |

## 二、待做项（本次未实施，仅记录）

### 待做 1：基线结果跨轮缓存（预计省 Phase3 的 30~50%）

**问题**：Phase3 每条经验都要跑一次**基线**（不加经验的生成）。而基线**只依赖任务**，
不依赖经验 —— 同一条 audit 任务在轮1/轮2/轮3 被反复用作基线，每次都重跑。

**方案**：
```python
# 以 (task_id, samples) 为键缓存基线通过率
cache: dict[tuple, float] = {}
def baseline_of(task, samples):
    key = (task["index"], samples)
    if key not in cache:
        cache[key] = self._joint_pass_rate([task], provider, samples=samples)[0]
    return cache[key]
```
**风险**：低。基线结果在运行期内是确定的（同一任务、同一配置、temperature=0）。
**注意**：缓存放内存即可，不必落盘（模型/配置变了缓存就该失效）。

---

### 待做 2：Phase2 多 Agent 协作并行（用户特别提出）

**现状**：Phase2 的 rollout 已按任务级并发（`_map`），但**单个 rollout 内部**的
四步流水线（Planning → CodeGen → Repair → Verify）是**串行**的，
且一次 rollout 内要跑「首轮 + 修复轮」两次。

**用户要求**："第二阶段需要多 agent 协作"——即把多 Agent 的思想用于**并行探索**，
而不是单条链路串行。

**可选方案**（需先设计再实施）：

| 方案 | 做法 | 预期收益 | 风险 |
|---|---|---|---|
| **A. 并行采样 + 投票** | 同一任务并行跑 N 条独立 rollout（不同 seed/温度），取多数决或最优 | 提高单任务质量，但**不省时间**（总调用量 ×N） | 成本上升 |
| **B. 分工协作** | Planning 与 CodeGen 拆成不同并发单元（如同时探索多个修复方向） | 中等 | 需改流水线契约，改动大 |
| **C. 修复轮并行** | 首轮失败时，并行尝试多个修复策略（而非串行重试一次） | 缩短修复耗时，提高修复成功率 | 需设计多策略提示词 |

**我的建议**：先做 **C**（改动小、收益明确），再评估 **A**。
**B 需要先明确"协作"的方法学定义**（否则可能只是"并发"而非"协作"，
与 DOCX 的四步 Agent 设计冲突）。

---

### 待做 3：跳过必然失败的修复轮

**问题**：`repairs=1` 意味着首轮不达 A 就再跑一遍完整流水线。
但实测 **231/303（76%）** 是 `seed_grounding_failure`，其中相当部分是
`fail/fail`（功能安全都不通过）——这类任务修复成功率很低，白跑一次。

**方案**：若首轮是 `fail/fail` 且安全证据显示"完全没做对"，跳过修复。
**风险**：会漏掉少数可修复案例。建议先**离线统计**（用已有数据）
"fail/fail 任务修复后的成功率"，若 <10% 再实施。

---

### 待做 4：LLM 调用级并发（而非任务级）

**现状**：并发是**任务级**的（一个任务 = 一个线程，内部串行 6~12 次调用）。
若某任务有 12 次调用、另一个只有 3 次，线程数固定时**负载不均**。

**方案**：改为"调用级"调度（全局调用队列 + 固定大小线程池）。
**风险**：高。四步流水线有**数据依赖**（后一步需要前一步输出），
不能简单拆开；需要引入更复杂的编排（如 DAG 调度）。
**建议**：暂不做，收益不确定。

---

### 待做 5：Level 4 的彻底清理（视用户后续决定）

**现状**：A7 只是**关闭生成**，`level4.py`、注入逻辑、相关测试全部保留。
**待决定**：若确认永久不需要，可删除代码（约 5 处文件、13 处引用）。
**建议**：**先保留** —— 消融实验（A3~A6）依赖它，且删了就无法回归验证
"L4 到底有没有用"这个结论。

## 三、改动后的预期耗时

以 874 任务全量估算：

| 阶段 | 旧配置 | 新配置 | 说明 |
|---|---|---|---|

| Phase2 ×3 轮 | ~1.5 小时 | ~0.6 小时 | 并发提升 |
| Phase3 ×3 轮 | 5.3 小时 | **~1.3 小时** | 并发 8 + 无 L4 |
| 最终评测（298 条） | 0.7 小时 | ~0.3 小时 | 并发提升 |
| **合计** | **~11 小时** | **~3.5 小时** | |

密切观察错误率（若大量 429/超时，需下调）。
