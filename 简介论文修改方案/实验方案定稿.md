## 1. 当前 baseline 盘点

### 1.1 九条方法的定义与实现位置（唯一入口）

九条方法由**同一个 runner** 运行：

```text
methods/workflow_baselines/run_true_agent_workflows.py
  --only-traditional  → 四条 Prompt baseline
  --only-agents       → 五条 Agent baseline
  （都不加）           → 九条全跑
```

`methods/prompting_baselines/run_prompt_baseline.py` **只是桩**：只打印提示词，不调模型、不跑 Docker。四条 Prompt 的真实实现也在上面的 runner 里。

### 1.2 四条 Prompt baseline

| 表格行名 | 请求次数 | 差别只在于 | 对应实现 |
|---|---:|---|---|
| Greedy | 1 | 直接生成 | `run_true_agent_workflows.py` 的 `direct_workflow` |
| Greedy + Secure Prompt | 1 | 追加安全提示 | 同上 |
| Chain-of-Thought | 1 | 追加思维链 | 同上 |
| Chain-of-Thought + Secure Prompt | 1 | 思维链 + 安全提示 | 同上 |

四条均为**单次请求**，没有多阶段、没有自测反馈、没有修复轮，fidelity 判定"不适用"。

### 1.3 五条 Agent baseline 与 fidelity 合约

`methods/workflow_baselines/fidelity.py` 用**可机检的合约**保证阶段没有被简化成单 prompt：

| 表格行名 | 必需阶段（缺一即 fidelity FAIL） | 最少模型调用 | 失败时必须出现的阶段 | 上游依据（代码注释所记） |
|---|---|---:|---|---|
| AutoSafeCoder | programmer → static_review → validation | 2 | fuzz_validation_repair | `AutoSafeCoder_official/main.py` |
| AgentCoder | test_designer → programmer → agentcoder_epoch | 2 | — | `AgentCoder_official/AgentCoder/` |

## 2. 方法侧现状（决定实验怎么设计）

| 实验 | 规模 | 结果 | 结论 |
|---|---|---|---|
| 训练侧 D_gate 三臂（09-25） | 298 题单次生成 | 无经验 55 / 原库 68 / 停用后 70 | 原库 vs 无经验 p=0.0854，Holm 后不显著 |
| 冻结后独立评测（09-25，对齐 semantic 检索） | Base 115 + Plus 140 | Base 有库 6 / 空库 5；Plus 有库 41 / 空库 40（修复后） | **净 +2 题，不显著** |
| 三分支对照（09-23） | D_grow 273 | 串联+1 次修复 95 / 同方案三采样 87 / 三思路 88 | 三思路对比采样 p=1.000，无优势 |
| HSK 分层消融 A1–A6（09-18） | 15 题 × 1 轮 | 六组 Joint 全 0/3 | L4 与 L2/3 拆分无收益（负面） |
| 检索策略对比（09-16） | 24 题 | 不注入 7 / 检索器 6 / LLM 直选 7 | 检索无净收益 |
| 反过度防御（09-18） | 6 题 | base 2/6 → contract_freeze 4/6 | **唯一正向干预**，样本小 |

**读法**：方法链路（多阶段生成 → 提炼 → 门控 → 冻结）**能跑通且可审计**，
但**"经验注入带来 Joint 提升"这一条在独立评测上还没有被验证**。
这直接决定了第 3 节的设计重点：不是再加臂，而是先把**主对照做干净**。

## 3. 对图片第三/四/五部分设计的评审

### 3.1 原样保留 ✅

| 图片中的项 | 评价 |
|---|---|
| 消融 1：**Full (Ours)** | 必须保留，作为所有 Δ 的基准行 |
| 消融 2：**消融状态机负向反馈**（只学 B→A，去掉 B→C 的反向规则） | **最有价值的一条**。B→C（过度防御）是本方法的形式化贡献，必须证伪式检验 |
| 消融 3：**no Agent**（去掉经验总结 Agent，退化为字符串模板） | 保留，直接对应"元认知提炼"这一贡献 |
| 消融 4：**Self-Evolution**（只用 M_0，关闭 Phase 2） | 保留，对应"自进化"贡献 |
| 消融 5：**Memory / HSK-Tree**（零经验裸跑） | 保留，但它其实是**主对照**而不是消融——见 3.4 的重新归位 |
| 第四部分：数据集分区随机化 | 保留，方向正确；按 3.2-E5 细化 |
| 第五部分：跨语言迁移矩阵 | 保留，这是本工作最有区分度的卖点；按 3.3 删减列 |

### 3.2 必须增加 ➕

| 编号 | 新增臂 | 为什么必须有 |
|---|---|---|
| **A6** | **w/o Gate2**（无独立有效性门控：候选生成即入树） | 图片只消融了"有没有经验库"，没消融"门控有没有用"。审稿人一定会问："你的三类门控到底筛掉了什么？" |
| **A7** | **w/o Gate3**（无 H_pass 回归门控） | 同上。且有现成反例证据：旧实现 `functional_regressions` 被硬编码为 0，过度防御**永远测不出来** |
| **A8** | **w/o Active Replay Scheduling**（随机回放 vs 受控调度） | 图片里完全没有调度消融，而"防长尾饥饿"是方法自己声称的机制 |
| **A9** | **w/o Language Leaf**（只用语言无关不变量，去掉 L4 语言叶） | 跨语言那一节要证明"叶节点有价值"，就必须有这一臂；否则跨语言结论只是"prompt 迁移" |
| **A10** | **w/o Contract Freeze**（去掉"禁止发明契约外前置条件"约束） | 这是全项目**唯一测出正向收益**的干预（33%→67%），不消融它等于把最强的机制留在暗处 |
| **C1** | **Few-shot RAG（检索黄金补丁代码）** | 图片 RQ1 已列；这是"静态检索"对照，用来证明提升不是"把安全文本塞进 prompt" |
| **C2** | **Retrieval-only（只检索、不进化、不门控）** | 与固定 M_0 配对：一个测"有没有记忆"，一个测"记忆会不会更新" |
| **C3** | **Append-only（只追加、不门控不淘汰）** | 证明门控与生命周期不是装饰 |
| **C4** | **Self-Refine / Reflexion 式任务内反馈循环** | 当前九条 baseline 都是"生成+自测"，缺少社区公认的推理时修复基线 |
| **C5** | **等预算对照（token / 调用数对齐）** | CLE 的四步 + 检索 + 提炼天然比单 prompt 贵。A 会必问"是不是只是花了更多算力" |

### 3.3 建议删减 ➖

| 原设计 | 建议 | 理由 |
|---|---|---|
| HSK-Tree **六组**分层消融（A1–A6） | 压缩为 **2 臂：扁平列表 vs 树** | 六组已在 15 题上跑过，结论是"全无差异"；再跑六组是重复投入 |
| 三思路分支（branch） | **移出主表**，只作附录一句 | 273 题上 88 vs 87，p=1.000，无优势 |
| 五个模型全覆盖 | 主表 **3 个模型**（见 5.3） | 成本翻倍但不增加结论强度 |
| JavaScript | **全部删掉** | JS 验证器仍在完善（README 第 306 行），没有可信 harness |
| 第五部分中的 `SeCodePLT (Java) → SeCodePLT (Python)` | **降级为附录/加分项** | 反向迁移需要 Java→Python 的训练侧链路；先把正向做扎实 |
| 消融 5「Memory/HSK-Tree」作为"消融" | **改归主对照（Table 1 的一行）** | 零经验裸跑是**最重要的对照**，放在消融表里会被读者低估 |

## 5. 统计与预算协议（写进论文的 Evaluation Protocol）

### 5.1 检验

- **主指标**：Joint（同一份代码 F∧S），**预注册**。
- **配对**：同一 task_id 配对，**双侧精确 McNemar**（不用正态近似——小样本会假显著，项目里已踩过：一度用无校正正态近似报"显著"，实际 p=0.125）。
- **多重比较**：消融 10 臂、跨语言 5 目标 → **Holm 校正**，同时报告未校正 p，两者分列。
- **聚类**：按 Seed Family 做 bootstrap（10,000 次），报告 95% 区间。
- **重复**：每个关键臂 ≥ 3 个独立 seed/划分，报告 mean ± std。仅固定 `temperature=0` **不保证可复现**（项目已实测：同条件下 283/298 题代码 AST 变化）。
- **分母**：`unmeasured`（编译失败、超时、空代码）**不得当作 fail 也不得剔除**，单独成列并说明原因。

### 5.2 数据隔离（审稿必查）

- `D_source ∩ D_replay ∩ D_audit = ∅`，按 Seed Family 原子隔离。
- `(D_source ∪ D_replay ∪ D_audit) ∩ CodeSecEval-X = ∅`。
- **D_gate 不得同时用于选择与评估**：项目已记录"过滤决策与评分都用了同一 D_gate"的选择偏差。
  最终表必须另留一个**未参与筛选的留出集**，或明确标注该行仅为训练侧证据。
- 冻结后 `feedback_channel: disabled`，测试反馈不得回流经验库。

### 5.3 模型选择（修正当前矩阵的混淆）

| 角色 | 模型 | 说明 |
|---|---|---|
| **主模型（必选）** | `deepseek-v3.2` | **必须与方法训练的基座一致**，否则 Table 1 的对比无效 |
| 强模型（泛化） | `gpt-5.x` | 经验库冻结后直接挂载，**不重训** |
| 推理模型（泛化） | `qwen3.5-plus` 或 `glm-5.3-flash` | `--max-tokens ≥ 8192`，否则正文被 reasoning 吃光 |

> 当前 README 的 5 模型里没有 `deepseek-v3.2`，这一点必须先改。

## 6. 执行顺序、工时与成本（粗估）

按"先修主结果，再补消融"排序，每一步都有产物：

| 阶段 | 内容 | 规模 | 粗估工时（24 并发） | 前置 |
|---|---|---|---:|---|
| **P0** | 链路验收：9 baseline 冒烟，断言无 `environment_error`、无"全 0 陷阱" | 9 × 3 语言 × 2 题 × 2 subset | 1 h | — |
| **P1** | **Baseline 全量**：9 方法 × {Base, Plus} × {py, cpp, go} × 3 模型 | 9 × 255 × 3 × 3 = 20,655 | 1–2 天 | P0 |

| **P3** | **RQ1 主判决**：Ours vs 最强 baseline，配对检验 | 复用 P1/P2 | 分析 | P1+P2 |
| **P4** | **消融 8 臂**：每臂完整训练 + 冻结评测 | 8 × (874 题 × 3 轮) | **6–8 天** | P3 通过 |
| **P5** | **跨语言**：冻结 M* 直接挂 C++/Go/Java，不重训 | 2 臂 × 3 目标 × 255 | 1–2 天 | P3 |

## 7. 风险与 go/no-go 判据

### R1（最高风险）：主结果目前是"零效应"

09-25 的独立评测：Plus **41 vs 40**，Base **6 vs 5**。**255 题净 +2 题。**

在写下任何"提升"之前，必须先满足：

```text
GO 判据（三条同时满足）
1. 在未参与任何配置选择的留出集上，Full CLE 相对 w/o memory 的 Joint
   绝对提升 ≥ 3pt 且配对 McNemar 双侧 p < 0.05（Holm 校正后仍显著）；
2. Function 不得下降超过 2pt（防止"用功能换安全"）；
3. 该提升在 ≥ 2 个独立 seed / 划分上方向一致。
```

**不满足时的两条出路**（必须现在就和导师定，不要拖到投稿前）：
- **出路 A**：把论文从"方法有效"改写为"机制研究"——贡献改为
  "过度防御的形式化 + 门控/生命周期设计 + 大规模负结果与诊断"。这条对
  ICSE/ISSTA 的 "empirical study" 轨道可行，但对 "new technique" 轨道会被拒。
- **出路 B**：修方法再跑（当前最有希望的三个方向）：① 经验载荷（具体条件卡 vs 抽象原则，
  已有 oracle 上界 12.5%→62.5% 的观察）；② 内部测试-修复闭环（自生成测试在修复轮提供
  针对性证据）；③ 收紧 provisional 卡的使用门槛（现有 342 次注入中 338 次是 provisional）。

### R2：Baseline 的"原版性"质疑

五条 Agent 是重写实现。**建议**：论文正文把这个局限前置声明，并提供 fidelity 合约作为附录；
如果时间允许，至少把 1–2 条（AgentCoder、AutoSafeCoder，二者上游有公开仓库且可锁定 commit）
换成上游原版 + adapter。

### R3：D_gate 选择偏差

"停用后 70 vs 原库 68"这一结果，筛选与评分用的是同一个池。**不得写成泛化增益**；
必须补一个未参与筛选的留出集，或降级为训练侧证据。

### R4：跨语言 harness 覆盖

C++/Go 的 Base/Plus harness 齐全（各 230/280 个 `main.*`），可以进主表；
**Java/JS 的 CodeSecEval 验证器未完成**，只能走 PLT Java（Juliet）这条独立链路。
论文里必须按语言分别报告"实际验证覆盖"，不能写成"四语言全部端到端验证"。
（现有 DOCX 里"完成了多语言端到端验证"的表述必须改。）

### R5：成本口径

CLE 的调用数天然高于单 prompt。必须补 **Table 6 的成本列** 和 **C5 等预算对照**，
否则"提升"可能被解释为"算力堆出来的"。
