# 基于相关研究的论文与方法修改方案

## 说明

本方案只讨论一件事：related work 中已有论文对我们当前 SCT 论文的研究问题、方法设计和实验方式有什么启发。related work 本身只是证据来源，不是要把它原样改写成论文的一章。以下建议都对应当前《面向多语言安全代码生成的经验自进化方法》中的具体模块。

## 一 先调整核心研究问题

### 当前问题

当前方法容易被读者理解为“给 Agent 增加一个安全经验库，然后持续更新”。但 related work 显示，安全示例检索、失败笔记、通用程序记忆和运行时写回门控已经分别存在。因此“有记忆”本身不足以构成研究贡献。

### 建议修改

把核心问题改成：

> 如何把代码生成与验证轨迹中的安全修复知识表示为可检验的临时假设，并在后续独立任务上判断其适用范围、有效性和回归风险，从而形成可冻结的多语言安全经验库？

具体要在引言和方法概述中突出四个对象：

1. 经验不是一次性规则，而是可被后续证据支持或反驳的假设；
2. 经验来源不只是最终补丁，还包括初始候选、最终候选、验证变化和修复轨迹；
3. 经验写回必须经过独立任务验证和历史能力回归检查；
4. 最终评测必须在经验库冻结后进行，不能用测试反馈继续更新经验。

## 二 从安全代码生成论文得到的具体启发

### 1. 不要把安全示例检索等同于自进化

SecCoder 类工作说明安全示例检索可以改善跨漏洞类型泛化，DiSCo 和局部偏好优化说明安全知识也可以通过参数或偏好训练注入模型。这给 SCT 的直接启发是：论文需要设置“静态检索/固定经验”对照，证明提升不是只来自把相关安全文本塞进 Prompt。

建议新增两个对照：

- Fixed Memory：只使用 R0 生成的 M0，不允许 R1 更新；
- Retrieval Only：检索安全示例，但不保存候选经验、不做门控。

如果 SCT 只与无记忆 Agent 比较，无法证明“自进化”机制本身有效。

### 2. 使用联合指标，而不是只报告功能正确率

CoV-Eval、RealSec-bench 和 SecureVibeBench 都提示：能识别漏洞或通过功能测试，不代表能够生成安全实现。当前 SCT 已经定义了 `FunctionalPass`、`SecurityPass` 和 `JointPass`，这部分应提升为主指标，而不是附属指标。

建议将主要结论统一改为：

```text
JointPass = FunctionalPass ∧ SecurityPass
```

结果表必须同时报告 Function、Security、JointPass，并按语言、CWE、Base/Plus 拆分。

不能只用功能通过率证明经验有效，也不能把静态漏洞告警下降直接当作安全生成成功。

### 3. 加入仓库和场景复杂度的边界说明

RealSec-bench 和 SecureVibeBench 将评测推进到多文件、真实仓库和漏洞引入场景。它们对当前工作的启发不是要求立即复制完整仓库级任务，而是要求说明当前 CodeSecEval-X 主要评测什么、没有覆盖什么。

建议在论文中明确：当前任务以函数级或受控 harness 为主；多文件依赖、构建系统和真实部署配置不是当前实验的完整覆盖范围；Go/C++ harness 能验证目标语言行为，但不等同于完整仓库级安全性。

## 三 从验证和自修正论文得到的具体启发

### 1. 将当前任务修复和跨任务经验学习分成两条链

Self-Debugging、SCoRe 和 ReVeal 主要研究如何利用编译器、测试或工具反馈修复当前候选。当前 SCT 的区别应写得更清楚：

```text
任务内链路：候选代码 → 工具反馈 → 当前任务修复
跨任务链路：初始候选/最终候选/验证差异/修复轨迹 → 候选安全经验
```

建议在数据结构中分别保存 `initial_code`、`final_code`、`verification_before`、`verification_after`、`repair_trace_summary` 和 `failure_root_cause`，证明经验来自可观察的修复变化，而不是模型事后凭空总结。

### 2. 不要完全信任模型自生成的测试

自生成测试的质量和覆盖率可能不足，甚至会给模型错误反馈。因此自生成测试只能作为辅助信号；安全晋升至少需要外部测试、静态分析或目标语言 harness 中的一项独立证据；还应报告“模型自测通过但外部安全测试失败”的案例。

### 3. 增加保守修复策略

已有研究指出，模型在没有可靠反馈时可能把原本正确的代码改坏。建议只有验证结果改善或保持不变时才接受修复；如果功能通过但安全失败，不允许以功能提升覆盖安全退化；每轮修复都要记录是否改变了已通过测试。

## 四 从 ReasoningBank 和 ReMe 得到的记忆机制修改

### 1. 经验应保存抽象策略，但必须安全专门化

ReasoningBank 说明压缩成功和失败轨迹为策略，比直接回放长轨迹更适合跨任务复用。当前 SCT 的 `principle` 方向是对的，但需要增加安全专门字段，避免退化为通用思维提示。

建议每条经验至少包含：

```text
trigger_context
security_invariant
recommended_action
unsafe_alternative
language_adaptation
non_applicable_boundary
evidence
status
```

其中 `security_invariant` 是必须满足的条件，`unsafe_alternative` 用于说明看似合理但会留下漏洞的写法，`non_applicable_boundary` 防止经验过度泛化。

### 2. 从 ReMe 借鉴更新和淘汰，而不是只做追加

建议把当前二元的 `promote/reject` 扩展为：

```text
provisional → supported → narrowed
                         ↘ demoted / retired
```

当后续任务发现经验只在较窄场景有效时，应收窄触发条件；当经验造成安全或功能回归时，应降级或退役。这样 SCT 的“自进化”才不只是不断加规则。

### 3. 增加经验证据状态

为经验增加支持证据数量、反驳证据数量、未决使用次数、最后验证轮次、适用语言和 CWE、当前状态及状态变更原因，把“经验是否可靠”从一句自然语言变成可审计状态机。

## 五 从 CodeMEM 得到的边界启发

CodeMEM 主要解决 AST、仓库结构和会话历史保持问题。对 SCT 的启发是：安全经验检索不能只按 CWE 文本相似度，还应考虑目标语言、函数签名、输入来源、敏感操作和 harness 约束。

建议将检索键扩展为：

```text
(CWE, source type, sink type, operation, language, signature, harness constraints)
```

同时明确二者目标不同：CodeMEM 减少仓库上下文丢失和会话内错误重复；SCT 诱导跨独立任务可迁移的安全假设。

## 六 从 SAFENOTE 和 Safety Sidecar 得到的门控修改

### 1. 借鉴错误分类，但不要只保存失败笔记

失败根因至少拆分为：安全原则缺失、安全原则误用、功能回归、目标语言 API 或类型错误、harness 接口错误、资源/超时/环境错误。它们应进入 `failure_root_cause`，并用于决定是否值得生成候选经验。

### 2. 借鉴验证后写回

编译、功能测试和安全分析可以共同控制记忆写回。当前 SCT 应将 D_gate 的晋升条件写成真正的闸门：

```text
质量合格
∧ 独立任务 JointPass 提升
∧ 历史任务无安全回归
∧ 功能退化不超过 ε
```

如果当前 PLT 只有语法和静态安全检查，论文必须标注为训练侧可执行门控的子集，不能宣称完成完整的三层动态门控。

## 七 从 experience-following 研究得到的关键修改

错误或不适用的经验一旦被检索，可能让后续任务产生相似错误。因此建议：

1. 记录 `experience_id` 和命中原因；
2. 记录生成结果实际采用了哪些经验；
3. 后续任务出现反例时更新经验适用边界；
4. 对高相似但高失败率经验增加风险惩罚；
5. D_gate 检查经验是否会在相似任务上传播错误。

最重要的是保留 prequential 隔离：任务 i 产生的经验只能影响后续任务，不能立刻回写并再次影响任务 i。

## 八 对当前 R0、R1、D_gate 的具体改法

### R0 改法

增加漏洞触发条件、修复前后差异、语言无关原则、语言特定实现提示和训练侧验证后端；区分“动态验证通过”和“仅语法/静态检查通过”。

### R1 改法

从“只做失败反思”改为“成功差异 + 失败根因”双通道：成功轨迹提取使 JointPass 提升的关键动作，失败轨迹提取缺失原则、错误适用范围和语言 API 误用；多个相似任务聚类后再生成候选经验；单条任务特判不能直接成为候选经验。

### D_gate 改法

质量门控检查答案泄露、样本特判、边界明确性和冲突；有效性门控检查未参与生成的 D_gate 上 JointPass 是否提升；回归门控检查历史已通过集合上是否出现安全回归、功能退化、编译失败或过度防御；出现冲突时执行 narrow、revise 或 demote，而不只是 reject。

## 九 对实验方式的具体修改

### 1. 增加机制级消融

建议至少加入无 M0、只有 M0 没有 R1、append-only 没有 D_gate、没有回归门控、没有不适用边界、只使用最终代码不使用修复轨迹、只使用语言无关经验，以及允许隐藏测试反馈进入记忆的泄漏对照。

### 2. 分离同语言和跨语言效果

至少报告 Python 经验到 Python、Go、C++ 的迁移，以及语言特定经验到对应语言的效果，证明多语言迁移而不是单纯的提示增强。

### 3. 增加记忆传播风险指标

报告错误经验命中率、经验命中后的失败率、同一经验导致的重复错误比例、经验被收窄/降级/退役的次数，以及经验加入前后相似任务的 JointPass 变化。

## 十 论文中必须诚实写出的实现边界

当前 PLT 不一定为每个任务提供完整的目标语言动态 harness，因此要区分：

```text
完整 harness：可报告 Function、Security、JointPass
只有静态检查：只能报告语法/静态门控结果
```

CodeSecEval-X 的 Base/Plus 最终评测必须在 M* 冻结后执行，隐藏测试结果不能返回给经验生成和门控流程。论文还应报告 API 空 content、超时、重试、Go/C++ 编译失败、harness 缺失、Docker 资源限制和目标语言适配失败。

## 十一 推荐的最终论文主线

```text
安全代码生成不仅需要生成正确答案，
还需要学习哪些安全原则在什么上下文中成立。

SCT 从验证轨迹中抽取结构化安全假设，
通过 prequential 隔离和独立门控控制其传播，
再在冻结经验库上进行多语言联合评测。
```

这个主线比“提出一个会不断增加经验的 Agent”更能回应 related work 中的共同问题：静态记忆可能传播错误，自修正可能改坏正确代码，功能正确和安全正确不能混为一谈。

## 十二 修改优先级

### 必须优先完成

1. 将经验表示扩展为带触发条件、不变量、不适用边界和证据状态的安全假设；
2. 明确 R1 的成功差异和失败根因双通道；
3. 把 D_gate 的有效性和回归判定落到可计算指标；
4. 统一论文主张与 PLT 当前实际验证能力；
5. 增加固定 M0、append-only 和无记忆等机制消融；
6. 单独报告 Base/Plus、语言和 JointPass。

### 第二优先级

1. 增加经验 narrow、revise、demote、retire 状态；
2. 记录经验命中、采用和反例传播；
3. 增加 Python 到 Go/C++ 的跨语言迁移实验；
4. 报告自生成测试与外部测试不一致的失败案例。

### 后续扩展

1. 更大规模仓库级任务；
2. 经验图谱和自动冲突求解；
3. 跨模型、跨数据集的长期经验迁移；
4. 参数级训练与外部经验库的联合更新。

## 总结

related work 对 SCT 最重要的提示不是再增加几个引用，而是推动研究方式发生四个改变：从静态经验检索转向轨迹诱导，从永久规则转向可证伪假设，从简单写回转向独立有效性和回归门控，从单一安全分数转向功能与安全联合、同语言与跨语言分解评测。论文只要围绕这四点修改，方法贡献和实验可信度都会明显增强。
