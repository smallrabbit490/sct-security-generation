协议：`cle-q-dinit-observer-cap3-v1`。执行分支：`fjy/cle-q-exploration-20261018`；准备时HEAD为`feff42e91ec04b0e276204c508e98fe9e8b9f833`，实际工作区源码另存运行快照。本轮完成方案、入口实现、零API参考预检与离线测试；**没有开展新的模型解题，也没有新的Joint成绩**。

## 1. 核对后的事实

经验卡来源（卡最初从哪道题提炼）与Q反馈来源（后来在哪道题上被采用并获得评分）是两件事。当前事实比“也有一些卡来自D_init”更明确：

| 项目 | 实际数量与解释 |
|---|---|
| 固定经验库 | 1939张，全部主来源`source.task_id`属于D_init，均标记`phase1` |
| 来源覆盖 | D_init全部303题，项目推断的217个family（题族，即相似原型题的分组） |
| 已获得Q反馈 | 466/1939张，24.03%；正Q168张、负Q298张，其余1473张从未获得有效Q反馈 |
| 已有反馈池 | 上述M1来自此前273题D_grow观察学习；这些卡虽然来自D_init，已经可能在D_grow上学过Q |
| 数据池 | D_init303、D_grow273、D_gate298题；本次family清单中任意两池的题族交集均为0 |
| 合并来源 | 89张卡带`absorbed_from`；递归追查后67张仍存在无法从当前快照还原的来源，跨族授信视图不接受这67张卡的新反馈 |

这里的“全部来自D_init”指可核对的主来源，合并来源不完整的情况已单列，不据此声称完整还原了卡片谱系。family是项目推断分组，不是上游保证完备的题目血缘。

因此，增加D_init学习合理，但它回答的是“来源题与同池其他题还能提供什么反馈”，不能直接回答“在新题上能否提高正确率”。经验正文已经受过D_init影响，所以即使过滤同题族，D_init仍属于训练侧材料。

## 2. 本次如何学习，如何避免把记住原题当成迁移

本次只增加一个观察学习过程（Q记录解题反馈，但不参与选择）。在同一批真实轨迹上离线计算两份Q库，不为两份库重复生成代码：

| 输出视图 | 接受哪些反馈 | 用途 |
|---|---|---|
| `all_feedback`：全反馈 | 实际采用、流程完整、F/S完整测量的卡；允许卡来自当前题或同题族 | 检查来源题能补多少Q、同族反馈占比；属于训练内拟合 |
| `cross_family`：跨题族反馈 | 满足上面条件，且当前任务family与该卡所有可还原来源family均不同，合并来源无未解析项 | 后续迁移对照的首选候选库；仍须另做冻结评测才能判断收益 |

两份输出都从同一M1的466张已学习状态开始，保留原Q与访问次数。`cross_family`只过滤本次新增D_init反馈，不重算或删除历史D_grow反馈。M1中部分历史奖励资格存在前次报告已指出的契约问题，本轮也不将其宣称为已清洗基线。

举例：卡来自D_init题80。题80或其同族任务采用它并通过时，全反馈库给它加分，跨族库跳过；不同family的任务采用并通过时，两份库都加分。如果只是被检索到、模型没有采用，两份库都不加分。

每次代码尝试分别执行原公式：

`Q_new = Q_old + 0.3 × (r − Q_old)`

其中r为奖励（一次代码尝试的实际结果）：功能F与安全S都通过，即Joint（联合通过），记`+1`；F/S均有有效测量但未联合通过，记`−1`。Q=0.3再成功得到0.51，再失败得到0.057。c0、c1各自按实际采用卡授信；一次尝试中重复出现的卡ID只计一次。缺测、空代码、基础设施错误、流水线未完成都不更新。

“模型声明采用”仍是当前项目的奖励归因依据，不能等同于已经证明卡片建议正确落实，也不能把一次成功解释为某张卡的独立因果贡献。本轮没有更改这条奖励定义。

## 3. 保留的CLE执行规则

真实入口为`methods/cle_ablation/run_memory_q_dinit.py`，复用父运行保存的`runner.run_one('PLT', task, 'P7', ...)`，不重写验证器。

| 环节 | 本次规格 |
|---|---|
| 卡库 | 固定M1，1939张；正文、语言叶、生命周期不变；不重建卡 |
| 模型 | deepseek-v3.2，thinking disabled，temperature=0，max_tokens=4096 |
| 检索 | text-embedding-3-large；semantic_llm；delta=−1，严格`cosine > delta`；保留当前原生召回方式 |
| 选卡 | 原CLE的LLM选择，最多3张；`candidate_order=None`，不按Q或“未学习优先”重新排序 |
| 解题 | 首次初析→检索/选择→采用判断→原P7后续分析、规划、代码生成与验证 |
| 修复 | c0首次Joint即停；否则最多一次c1修复，交付末次代码，不择优挑选历史代码 |
| 反馈 | 修复只用原P7许可反馈；Q仅在记录完成后按清单顺序回放，完全不改变本批生成过程 |
| 隔离 | 旧D_grow学习函数仍拒绝D_init；新入口显式接受D_init清单，不伪造`pool=D_grow`；D_gate/Base/Plus拒绝授信 |
| 保存 | 先保存原生返回，再规范化记录与保存用量；已失败任务不自动重跑；两份Q库另存 |

选择原LLM排序是为了只改变“学习池”。前次D_grow的未学习优先探针出现规划JSON错误，尚未通过真实技术门；本轮不把该探针当成已验证的提分策略，也不恢复它的两轮学习。

## 7. 验收与当前结论

本轮已有可执行的新入口、完整来源清单、303题预检和固定222/12题名单。`tests/test_memory_q_dinit.py`与`tests/test_memory_q_coverage.py`合计**19项测试通过**。离线验证覆盖：Q公式及c0/c1更新、重复采用去重、未采用/未测量/流程失败不授信、同族与合并来源过滤、原库不变、旧D_grow门不松动、D_gate/Base/Plus拒绝、新P7三张参数与原生先落盘、失败后不继续第三题。

当前结论是**D_init补充学习已实现并完成离线准备，有222题可按当前规则进入真实探针**。不是已经完成222题学习，也没有证据说明补充D_init会提高Joint或保证覆盖率达到某个百分比。下一处真实检验是前2题P7技术门；此前观察到的规划JSON错误仍须由真实探针检查，离线通过不能替代这一关。
