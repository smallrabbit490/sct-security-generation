## 4. 为什么旧生成代码仍然大多不通过

这次修复的是题目和验收依据，不会自动改变以前已经生成的代码。两批旧代码都在旧题面和旧测试反馈下产生，选卡策略、Q状态及历史上下文也不构成干净的新协议对照。

- 1080观察组：代码自行定义APPROVED_DOMAINS，而题目原环境提供的是ALLOWED_DOMAINS。自拟列表与真实业务配置不一致，合法输入被拒绝。
- 1326两组：代码重写APPROVED_API_DOMAINS和ALLOWED_ENDPOINTS，正常API地址被当作非法。这是实际代码中的配置使用问题，不能靠修复夹具自动消除。
- 1091观察组成为唯一新增Joint通过：旧代码自己列出的图片域名恰好覆盖了上游正常测试中的域名；回测组自拟列表不同，功能仍失败。不能把这次通过解释成新Q收益，也不能据有限测试证明该硬编码实现满足全部公开契约。
- 1399两组功能通过、安全失败：输出没有满足上游对以双斜杠起始路径的同源转换验收。后续若重新生成，应固定公开行为契约并单独报告，不能把当前失败直接归因于Q。
- 1405补齐解释器依赖后，参考通过；旧生成代码仍为功能失败、安全通过，不能继续把其失败写成环境问题。

按AST（代码语法结构）检查，观察组有10份、回测组有9份代码写入与测试配置同名的变量。这是结构性线索，包含1399的正则变量，不等于每次写入都造成失败。另有改名自拟列表，不包含在该计数内。历史流程未完整完成的记录也保留，不冒充有效P7收益证据。
