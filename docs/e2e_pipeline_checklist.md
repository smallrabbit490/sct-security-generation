# CLE 实验链路检查清单（端到端跳数校验）

> 建立原因：2026-09-21~22 期间**连续三次**因"每段代码都对、但中间少一跳"而白跑整轮实验：
> 1. D34：`_same_task_bonus` 机制写好了，但 4 个调用点构造的 query 里**没有 `task_id`** → 加权恒为 0
> 2. 方案 A：经验**确实入池**了，但 Phase1 传的是 `retriever=None` → **没有检索入口**
> 3. D35：周期落盘线程写好了，但放在 Phase2 之前 → **Phase1 全程无保护**
>
> 共性是：**单测通过 ≠ 链路通畅**。单测验证"函数对不对"，链路校验验证"数据到不到得了"。
> 本清单专治后者。

---

## 使用时机

改动以下任一项后**必须**逐条走一遍本清单，再启动长跑：

- 新增/修改跨模块传递的字段（如 `source.task_id`、`task_description`）
- 新增/修改检索、注入、提炼、落盘任一环节
- 调整并发结构（线程池、锁、信号量）
- 修改运行生命周期（启动时、每轮、结束时各写什么）

## 一、数据跳：值到底有没有传到

对每一条"跨模块传递的数据"，回答三问：

| # | 检查项 | 本次踩坑 |
|---|---|---|
| 1.1 | **写入方**是否真的写了这个字段？（打印/落盘验证，不要只看代码） | `hpass` 原只有 `{cwe, task_id}` |
| 1.2 | **传递方**是否原样带了它？（中间层最容易丢） | query 构造时漏了 `task_id` |
| 1.3 | **读取方**是否真的读到了？（非空校验 + 计数） | `_same_task_bonus` 恒返回 0 |

**验证手法**：在产物里**计数**，而不是在代码里"看起来对"。例如本次用真实产物算出
`Phase1 修复轮 14/14 检索到 0 条经验`，一眼定位断链。

## 四、并发跳：高并发下还成立吗

| # | 检查项 | 本次踩坑 |
|---|---|---|
| 4.1 | 共享容器（池/树）的写入是否都在锁内？ | worker 线程写池 → 新增 `_pool_lock` |
| 4.2 | 锁内**没有**阻塞调用（网络/LLM）？ | 锁内若调 LLM 会把所有线程串行化 |
| 4.3 | 信号量等待**不在**超时计时窗口内？ | 闸门放在 `join()` 内 → 排队时间被算进硬超时 |
| 4.4 | 任务内部并行后，总在途量是否仍受控？ | 80 workers × 8 并行打分 = 640 → 需全局闸门 |
| 4.5 | 嵌套线程池会不会耗尽线程？ | `_map` 内部再建池要评估 |

## 五、失败跳：出错时会怎样

| # | 检查项 | 本次踩坑 |
|---|---|---|
| 5.1 | 会不会**静默**失败？（吞异常、日志无输出） | 挂包后在重试里空转，日志静默 10 分钟 |
| 5.2 | 会不会**无限**重试/等待？ | 每次 90s × 3 = 270s/调用，单候选几小时 |
| 5.3 | 失败时能不能**续跑**？ | 卡死不写经验池 → 无法 `--resume-from` |
| 5.4 | 清理/启动类操作失败会不会**干掉整轮**？ | `unlink()` 被安全策略拦下 → 启动即崩 |

**已落地的兜底**：周期落盘（D35）、连续失败熔断（D36）、重试退避。
判据很简单：**宁可大声失败，不要静默空转。**

## 七、最小验证流程（推荐顺序）

1. **单测**：函数行为正确（已有 350 条）
2. **产物计数**：用真实产物统计"命中/未命中"，验证每一跳
3. **小规模真跑**：60 任务 / 3 轮，约 20 分钟
4. **对照评测**：Base/Plus 的 mstar vs nomemory
5. **再启动长跑**：此时才值得花几小时

第 2 步是本清单的核心 —— **它是唯一能在几分钟内发现断链的手段**。
