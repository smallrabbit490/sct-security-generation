## 3. 怎样组成一对可比较的记录？

1. **Codex按原实验、task_id和repeat配对。** 同一题的r1与r1、r2与r2对应，不把某次有卡成功与另一次无卡失败拼成一对。
2. **Codex核对干预之前的信息。** 公开`task_description`、实际见卡前`initial_analysis`、模型版本及参数、原验证器、每次最多一次修复的规则一致；核对原P7提示模板，确认没有额外结构或提示改动。计划和采用结果属于读卡后的产物，不要求两组相同。
3. **Codex核对实际供卡。** 无卡条件在首次和修复都必须没有经验文本；有卡条件保存实际呈现卡文、卡片顺序、采用/拒用和后续计划。有卡组没有选到卡或拒绝全部卡的记录仍留在完整流程比较中，另列实际读到卡、实际采用卡的数量。
4. **Codex核对原始代码和验证记录。** 首次使用`attempts[0]`，最终使用原流程实际交付的`final`。已经首次Joint成功的代码直接作为最终代码；不挑两轮中成绩较好的代码替换原交付。
5. **Codex固定配对清单后再作差异归类。** 清单记录两份原文件路径、所属D集、family_id/近邻组、重复号、条件、模型和是否可测。缺一侧、输入不一致、验证环境不一致、响应模型无法核实分别列出原因，保留在覆盖统计中。

记忆标签、S4与FFS均在同题同重复中共享见卡前初析。原修复依各条件自己的代码和允许反馈进行；首次比较回答经验对第一次生成的影响，最终比较回答含原修复流程的交付差异。

## 4. Codex具体怎样查看两份代码？

1. **先核对题面与卡文。** Codex从公开功能、安全要求中列出需要实现的行为，并抄录卡片对应的操作建议。沿用S1的逐题功能、安全、Joint分类，区分公开要求充分、缺失、歧义与冲突；缺少信息却猜中测试的成绩单列说明。目标`ground_truth`和隐藏测试不作为卡片已有知识。
2. **逐对生成并阅读代码差异。** 左侧固定为无卡代码，右侧固定为有卡代码；分别展示首次与最终代码。忽略空白、注释和单纯改名后，再判断是否改变实际行为。自动diff只负责定位，行为分类由Codex读代码确认。
3. **对每个行为变化写清楚三件事。** “无卡代码怎样做”“有卡代码怎样做”“哪句卡文与该变化对应”。同时保留对应计划和实际代码行。计划写了但代码没做，登记为未落实。
4. **核对失败发生的位置。** Codex读取原验证器的断言和运行结果，将具体失败对应到代码分支、函数调用或数据修改；原验证材料缺失或同一代码结果冲突时，使用该记录原版本的验证器零API回放。参考代码和测试细节只用于事后判分与定位。
5. **单独查看修复。** 若两组第一次都失败，Codex对照各自修复前后代码，统计修复修正了什么、是否引入新错误；将首次差异和修复差异分开记录。

本轮保持所有已生成代码原样，不做人工最小修复。这样每个通过率始终对应有卡或无卡的真实原运行。回放遇到依赖缺失时登记具体环境问题，不安装替代验证器或重生成答案。

### 逐对代码记录的展示方式

| 题目/重复 | 卡片具体建议 | 无卡代码及行号 | 有卡代码及行号 | 实际行为差异 | 无卡F/S/Joint | 有卡F/S/Joint | 对应测试与判断 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 执行后逐对填写 | 实际入模原句 | 原文件链接与必要代码 | 原文件链接与必要代码 | 说明输入、操作与输出怎样改变 | 通过/失败/未测 | 通过/失败/未测 | 写明救回、损失或成绩不变的原因 |

主要64对及完整原卡复核32对全部完整审读。历史486对按冻结清单全部纳入，按题目集中审读两次重复，优先处理三项成绩有差异的代码，再完成成绩相同的代码；相同代码或相同差分复用已读内容的引用。结果中的“已审读”数量按实际完成登记。

## 5. 怎样统计经验影响代码的具体方式？

分类描述代码动作，不沿用固定三类结论；允许材料出现新类型。

| 代码行为 | 需要实际查看什么 | 统计内容 |
| --- | --- | --- |
| 保留或覆盖已有数据、模板、权限配置 | 是否重置外部字典、替换题面指定对象、自设模板或名单 | 涉及配对/题数，F/S/Joint救回与损失 |
| 改变函数接口、参数、返回值或输出格式 | 是否新增参数、修改返回结构、遗漏记录或使用错误分隔 | 同上 |
| 增加、删除或改变检查 | 检查是否符合公开要求，是否拒绝合法输入、遗漏危险输入 | 同上 |
| 改变检查与读取、执行的顺序 | 安全检查是否发生在敏感操作之前，是否使用了正确对象 | 同上 |
| 改变算法、API调用或异常处理 | 是否采用错误的解析、格式化、库调用或异常分支 | 同上 |
| 仅有文字或写法变化，行为相同 | 两份代码在任务相关行为上是否等价 | 数量及原验证结果是否一致 |
| 其他行为变化或依据不足 | 保存具体代码和待确认问题 | 单列，不强行归入已有解释 |

每种行为再统计四种对应情况：**卡文建议在有卡代码落实而无卡代码未落实；两组都已做到；卡文建议未落实或实现相反；代码变化在卡文中找不到对应建议。** 后两类用于定位采用、规划、实现及一般生成波动的问题。

同一对代码可以包含多种行为，分类表注明可多选，不能把分类计数相加当总配对数。每类同时给“涉及多少对代码”和“涉及多少道不同题”。

## 7. 结果达到什么条件，就写什么结论？

| 已有记录给出的结果 | 采用的结论 |
| --- | --- |
| 某批Joint救回多于损失 | “有卡在该批题目中净救回X次，Joint提高Y个百分点。”同时给区间和两次重复方向 |
| 某批Joint损失多于救回 | “有卡在该批题目中净损失X次，Joint降低Y个百分点。”逐项定位损失行为 |
| 救回与损失相等 | “该批Joint净变化为0”，分别列救回与损失，展示抵消发生在哪里 |
| 两次重复Joint均净增，题族95%差值区间下界大于0，主要Joint比较置换p≤0.05 | “有卡在本批对照中取得一致的Joint增益” |
| 功能、安全、Joint均净增，且三项Holm校正p≤0.05、各差值区间下界均大于0 | “三项通过率均提高”；否则分别陈述三项实测方向 |
| 卡文提出某操作、有卡代码执行、无卡代码未执行，并与原测试救回/损失对应 | “该代码变化与卡文建议一致，对应X次救回/Y次损失”，列原句、代码与测试 |
| 两组代码变化在卡文中没有对应建议，或读卡后未落实建议 | 归入一般实现变化或未落实统计，给具体数量和代码位置 |

整体有卡/无卡比较用于评估原流程中引入经验的效果；代码逐项对照用于识别影响路径。每条机制按实际审读的卡文、代码与验证登记。仅卡片ID被选中、仅声明采用、仅计划提及的记录，分别按各环节统计。

历史FFS只分析已保存且符合配对条件的记录；其结果表述为“已保存配对样本”。门槛用于解释本轮证据，所有固定配对、负结果及成绩不变案例均完整分析，不因未提分终止归类。

## 8. 按什么顺序执行和交付？

1. Codex核对原协议、所有配对和输入；主要64对名单已经保存，补齐完整原卡复核32对、486对历史候选的最终可用名单及未配对清单。
2. Codex复用原验证结果，必要时以原验证器零API回放原代码，先完成两批首次/最终三指标表及救回、损失清单。
3. Codex逐对阅读公开题面、入模卡、计划与两份代码，完成全部行为分类和逐代码表。
4. Codex完成按题族聚类的配对统计、重复方向和机制计数，核对每个主要结论能跳到具体代码与测试。
5. Codex另存《方向5：有卡与无卡代码及通过率对照分析》及逐对表；再按实测结果修订方向5叙事，供用户决定是否合入手动修改的周报。

**完成标准：**每对记录有真实原路径、明确输入资格、首次与最终F/S/Joint、修复次数、代码对照和审读状态；全部救回与损失有具体原因；行为计数能追溯到逐对表；模型和题集分开；未测、未配对和未能归因数量完整列出。计划完成与分析完成分开登记。

**费用与调度：**本轮新增模型/Embedding Token和HTTP预算均为0。只读取原记录并运行必要的本地原验证器，不调用dsh-tui或其他模型接口，不启动付费任务、不恢复排队全量、不新增监控。
