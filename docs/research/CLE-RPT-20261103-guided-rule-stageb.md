# 固定已验证的修复动作，能改善CLE提炼后的Joint吗？

**18/18单元完成测量、原生回放和逐题分析。** 原生提炼、固定动作加模型说明、仅动作规则的最终Joint分别为1/6、6/6、6/6。两种新规则相对原生均救回5、损失0，三个登记题族都有净收益。两种新规则最终分数相同；加说明组全部首次通过，仅动作组有两次用到修复。按事前规则保留仅动作卡作为必要的简单对照，同时保留说明组减少修复的观察，不自动扩大实验。

## 为什么继续改提炼方式？

[上一阶段](CLE-RPT-20261103-guided-zero-joint-stagea.md)在三道开发题上得到原卡0/6、手改4/6、通用规则6/6。命令题的手改限定没有稳定落实，通用规则则直接读取环境提供的权限名单。本阶段检验：把已验证的修复动作固定下来，整张卡都围绕这个动作生成，能否减少旧配方的干扰。

来源仍是算术1161、命令1337、API重定向676三个登记题族，涉及数值类型与外部策略对象两类机制。原验证器确认三份已存失败代码经局部删除后Joint：算术删除末尾整数归一化，命令和API删除覆盖环境策略对象的样例赋值。这些来源修复由程序提出并本地验证，未标成CLE模型自己完成的修复。

## 三组具体比较了什么？

1. 从公开上下文和代码语法树识别两类候选删除操作，不按题号或隐藏名单成员选择动作。用原验证器确认来源修复后Joint，再形成提炼材料。
2. 原生组调用原CLE提炼提示，输出正常完整卡；固定动作组保留预设动作和适用条件，模型只补充安全行为说明；仅动作组使用同一动作和条件，不调用提炼模型。
3. 三组均使用一张完整CLE卡、相同编号、相同模型和P7流程。同题同重复共享首次分析，六份首次分析全部精确复用；两次重复来自各自独立的已存响应。
4. 每单元最多修复一次，使用原验证器。原卡库和Q冻结，固定选卡。当前完整卡与上一阶段L2呈现不同，两个阶段的成绩分开。
5. 实际阅读六份提炼输出。命令可选说明擅加`strip()`，发布规则撤下这段无公开依据的说明，保留原始输出，不付费重写。原生组两张方向错误的卡保留为对照。
6. 完成生成后精确回放，并核对公开题面、实际卡片、采用记录、计划、代码和验证结果。连接中断只接续成功前缀，不重跑已完成代码。

固定动作来自人工设计的两类规则模板，程序负责识别、验证和编译。这一步验证的是受约束的提炼规则，尚未验证任意错误的自动归纳。

## 代码证据说明了什么？

**命令和API：原生卡把环境对象误认成缺失定义。** 命令重复2的首次代码已有样例名单；修复轮采纳卡后，计划明确要求保留五条样例命令并建立缓存，强化已有错误。重复1首次采纳卡并自设名单，修复轮拒卡后仍保留自设名单。API两次重复的首次代码均按卡要求定义样例域名和端点，修复后仍未撤掉。四份最终代码分别只删除替换赋值就恢复Joint。两种新规则的命令/API代码均读取环境策略对象，没有样例覆盖。

**算术：只提醒末尾别转整数，仍会漏掉前面的类型破坏。** 原生重复2把所有数字解析成float，修复轮又添加末尾转int。只修数字解析、只撤末尾转换均未通过；两处一起修才Joint。新规则同时说明字面量与运算结果类型，已完成代码保留两者。

**正确内容还需要通过采用和实现环节。** 两份仅动作算术代码首次没有完整返回采用编号，并保留错误转换；修复轮明确采用卡片并改正，两份均Joint。原生算术重复1首次拒绝正确卡，修复轮采用后通过。加说明组的两份算术代码首次即保留字面量与运算结果类型。内容、采用和实现分别记录，没有合成一个原因。

对五份最终失败代码完成七项局部回放：四份命令/API代码各撤掉自设策略赋值；算术分别仅修解析、仅撤归一化及两处合修。五份最终失败均有最小修法恢复Joint，正式模型成绩保持原样。

## 中断后怎样完成实验？

9个单元保存后触发累计200万Token预算门。用户批准提高到300万，只补齐原18单元；精确复用9个完整单元及未完成前缀后续跑，又保存2个。随后原代理连续TLS中断，代理握手失败、同一API地址直连超时。19:29原代理TLS 1.2握手恢复；零API演练再次核对11个完整单元和七个缺失边界后，仅接续缺失请求，最终完成18个。原失败、未知用量、完整响应及恢复段均保留。当前worker为0，本批已关闭新增派发。

新增97次物理请求：92次取得完整返回，其中58次服务端未返回用量；5次TLS失败的执行和用量保留未知。已报告116,863 Token，新未知用量共63条。加上此前账本，累计已知1,046,655 Token、未知88条，已知及未知预留合计占用2,399,745 Token，上限3,000,000。六份首次分析的复用未新增HTTP。

## 本批结论和下一步是什么？

固定18单元、六份提炼、六份首次分析的精确回放及18项实际案例解读全部完成，没有剩余付费单元。预算恢复与真实网络补发分开记录，成功前缀没有重复派发。全量队列继续跳过。

**本批确认：固定来源修复已经证实的动作，明确环境对象由谁提供，并同时约束相关类型转换，可以提高这三个开发题族的最终Joint。** 本轮保留仅动作规则作为后续必备的简单对照；模型说明没有增加最终Joint，但减少两次修复，继续作为效率候选。下一步应冻结这两类动作规则，在未参与设计且实际会采用同卡的题目上验证迁移，并评估来源修复能否由CLE原流程稳定产出；本批不自动派发后续实验。
