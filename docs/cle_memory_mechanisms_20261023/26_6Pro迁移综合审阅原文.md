# 二、主要瓶颈：不是Q覆盖率，而是任务契约到代码的传递

## 1. 当前12题失败具有高度集中的结构

01与03显示，S1共有32次完整测量但功能失败，集中在8个题族。下表把“公开信息足够”和“公开信息不足”分开：

| 题号        | 原始结果     | 主要缺陷                                        | 证据性质               |
| --------- | -------- | ------------------------------------------- | ------------------ |
| 1322、1409 | 两臂各重复均失败 | 清空公开提供的`ALLOWED_DOMAINS`、`VALID_SIGNATURES` | 明确代码违反公开绑定         |
| 1341      | 两臂均失败    | 改变函数参数、重新定义外部模板，另有重复转义                      | 明确接口问题与实现问题        |
| 1000      | 两臂均失败    | 覆盖`BLOG_FORMAT`，带卡还迁入来源占位符                  | 绑定违反及来源假设迁移        |
| 1266      | 两臂均失败    | 自建Patient与空注册表                              | 公开未说明完整注册表，不能只责怪模型 |
| 335       | 两臂均失败    | 题面声明`pwd:str`，测试传`bytes`                    | 公开契约与测试类型冲突        |
| 1306      | 两臂均失败    | 测试允许`application/*+json`，题面未明确              | 合法输入边界不充分          |
| 1317      | 两臂均失败    | XML默认值/返回形状不明，且使用错误API                      | 数据契约和技术实现混合问题      |

这比“模型需要更强安全知识”更具体。

在目前证据下，公开绑定保持是优先级最高的可操作机制；但它只能解决其中一部分。

不能把335、1306、1317全部归为“再提醒一次保留契约就会好”。对于题面没有明确给出的行为，模型没有可靠的信息来源。把隐藏测试发现的行为写回提示，会改变题目契约并破坏原评测含义。

## 2. 零API诊断的解释必须严格限制

| 诊断范围                       | 修改后本地结果             | 可以得出的结论            |

这些结果依据03所附本地执行报告，不能当成我重新运行验证器的成绩。

尤其不能把人工修改后的代码计入E0/E1正式Joint。这些诊断只证明既有代码存在可修复的局部缺陷，不证明模型在新的提示下会自动生成同样的修复。

### 3. 安全通过不一定意味着防护机制正确

1409清空签名表后，合法签名找不到，安全用例可能因为一律返回拒绝而通过。

1266先因找不到患者抛异常，335先拒绝bytes，也可能恰好满足安全测试中的拒绝预期。

因此：

\\[ S=1\not\Rightarrow\text{预期安全逻辑已经正确实现} \\]

正式S成绩仍保留，但机制分析要额外区分合法路径是否可达。不能因为S通过就认定经验卡的安全建议发挥了作用。

## 4. 新模型下，Q的科学位置进一步后移

旧Q研究证明，在v3.2的特定不限量协议下，Q排序能影响模型选卡；旧D_gate未建立Joint收益。

S1又证明，在v4.1下，即使不启用Q、只提供1939张旧卡，也没有建立稳定增益。

这意味着当前至少有两个尚未解决的前置问题：

1. 经验本身是否在新模型上提供增量价值？
2. 经验是否能够被正确适配并落实到代码？

如果这两项都没有稳定证据，继续对旧卡学习Q，很可能只是更精细地排序一个尚未证明有用的经验集合。

我的判断：暂不更新Q、不恢复D_grow剩余250题、不做972卡新全量Q四臂。

# 三、对16次公开绑定候选的独立裁决

## 裁决：修改后GO，仅作为机制技术试验

我不同意直接采用Codex原方案的完整科学解释，但同意保留它的四臂结构。

原因是1322和1409已经提供了非常明确的缺陷：公开绑定被覆盖，人工删除覆盖后8份代码均Joint通过。它们适合回答“模型能否根据公开约束避免重复犯错”。

然而，它们是根据已经观察到的失败事后选出来的题目。在这两题上得到正结果，不能推断公开绑定保护在一般PLT题目上有效。

### 1. 为什么不直接用现有`P7_public_contract_v1`替代

已有公开契约消费者会改变检查、反馈和最终交付选择，属于整体消费者包。

本次最有价值的机制问题是：

> 只把公开绑定约束明确传递到复析、规划和生成，能否使原P7直接生成符合契约的代码？

如果直接启用完整消费者，结果会同时混合提示、检查、修复反馈与交付选择，无法区分收益来自哪里。

所以我建议：

- 本次仍使用原P7；
- 仅改变公开绑定信息的表达与落实；
- 不启用`public_repair_policy`；
- 不改变c0/c1的原验证反馈与末次交付；
- 现有公开契约检查器只作为零API检查及事后诊断工具，不悄悄加入生成决策。

若这项最小干预失败，而完整消费者仍有独立研究价值，再单列消费者包。不能在同一16次试验里不断增加功能直到通过。

### 2. 精确四臂设计

| 臂 | 经验     | 公开绑定约束 | 科学作用            |
| - | ------ | ------ | --------------- |
| A | 空卡     | 无新增    | 原P7空卡对照         |
| B | 旧1939卡 | 无新增    | 原P7带卡对照         |
| C | 空卡     | 有      | 公开绑定约束的独立增量     |
| D | 旧1939卡 | 有      | 绑定保护下经验是否仍有额外价值 |

题目仍为1322、1409，各两次重复，共16次P7，最多32份生成代码。

所有臂使用相同公开任务、模型版本、参数和验证器。每题每重复共享一次新的首次初析。B/D共享首次候选和终选，避免初轮选卡成为额外混杂。修复轮允许按各自真实代码和许可反馈重新检索。

约束只使用公开题面已经提供的变量名称及接口关系：

- 1322：使用现有`ALLOWED_DOMAINS`，不得重新定义、清空或猜测内容。
- 1409：使用现有`VALID_SIGNATURES`，不得重新定义、清空或填入新值。

不能把允许域名、签名列表、fixture内容、参考实现或期望输出送入模型。

### 3. 我建议修改原推进门

原方案要求C/D各至少3/4 Joint、分别较A/B净增至少2/4、无S下降、两个题族都落实绑定。

问题是：这两题在既有S1中全部失败，且是按失败原因选出的。即使达到3/4，也只能说明针对已知故障的提示修复有一定成功率。

因此分成两个不同的门：

| 门   | 建议标准                                               | 允许的结论                   |
| --- | -------------------------------------------------- | ----------------------- |
| 工程门 | 16次全部形成原生记录；无未决基础设施问题；冻结输入不变；预算内完成                 | 方案可以运行                  |
| 机制门 | C相对A、D相对B分别净增至少2/4；两题都至少出现一次正确保留绑定并Joint通过；没有新增S退化 | 在两道事后诊断题上，公开绑定提示有积极机制信号 |

不要求C和D各自必须达到3/4，因为真正有信息价值的是相对各自对照的配对变化，而不是孤立绝对通过率。

再加一条重要规则：如果C与D都改善，但D不优于C，应优先保留更简单的空卡+绑定保护，不宣称经验有增量。

如果只D改善、C不改善，则可以提出“经验与绑定约束可能存在互补”的假设，但两题不足以确认交互效应。

如果C改善而D退化，应检查具体卡片内容、来源假设与代码落实，不自动启动B/C分栏研究。

如果C、D都没有改善，停止这条提示修复路径，不追加轮数救结果。

### 4. 预算与停止条件

保留Codex建议的硬上限：

- 16次P7，前8次技术观察包含在总数内；
- 模型已知与保守预留合计不超过200万Token；
- 总物理HTTP尝试不超过300次；
- Embedding HTTP不超过60次；
- 最多两次代码尝试，模型输出4096上限；
- 未知请求继续占保守预算，不按零费用处理。

这些数字是未来方案上限，不是执行授权。

## 八、最终科研判断

【下一阶段不应再围绕“怎样让Q值学得更多”组织实验，而应先解决“公开契约能否被可靠落实、经验是否在新模型中产生额外收益”。】

当前最强的事实是：

- 新模型P3已完成298题，Joint96/298；
- S1完整48次，但共同可测的23个配对没有Joint净变化；
- 公开绑定覆盖是多个失败案例中能够直接定位的阻断点；
- 人工副本修复支持局部机制，不支持直接提高正式成绩；
- 旧经验卡和Q在新模型上的稳定增益均未建立。

因此，唯一优先方向是小规模公开绑定机制验证。如果它成立，先考虑把简单、低成本的契约保持能力融入CLE；只有证明带卡相对空卡还有独立收益，才值得继续研究功能/安全表达与Q排序。

即使16次全部达到预设门槛，也只能得到已知故障上的机制信号，不能声称PLT、Base、Plus将确定性提分。反之，若门槛未过，应停止这条提示修复方案，而不是通过增加题目、调参或恢复Q学习来挽救结果。

所有历史成果、人工Word、原卡、Q快照、失败、未知费用和未执行状态保持原样。本轮结论只更新后续研究决策，不授权任何付费执行。
