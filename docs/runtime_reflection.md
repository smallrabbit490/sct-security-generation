## 二、拖时间的具体环节（逐项量化）

### 环节 1：Phase1 单任务 307 秒 × 303 条 ÷ 5 并发 = 5.2 小时

实测单任务耗时分布：均值 **61.3s/条**（日志间隔），P90 71s，**最大 124s**。

推算单任务串行耗时 = 61.3 × 5 = **307 秒**。

**为什么单任务要 307 秒？** 本地实测一次"干跑"（无消融、单 worker）只要 **63.5 秒 / 6 次调用**。
差距 4.8 倍，来自：

| 原因 | 影响 |
|---|---|
| **修复轮**（`repairs=1`） | 首轮不达 A 就再跑一遍完整四步流水线 → 调用翻倍 |
| **失败任务占 76%**（231/303 是 grounding_failure） | 失败任务要跑满"生成→验证→修复→验证"，比成功任务慢得多 |
| **A4 消融生成 Level 4 叶** | 每个 seed 多生成 4 个语言叶（python/cpp/go/java） |
| **长尾木桶效应** | 5 并发下，一个 124s 的任务会拖住整批 |

### 环节 2：Phase3 审计 24 条用了 105 分钟（每条 4.4 分钟）

Phase3 每条经验的流程：
```
LLM 选择器挑任务
  → 对每个任务跑【基线】：生成 + 验证
  → 对每个任务跑【加经验】：生成 + 验证
= 2 任务 × 2 次生成 = 4 次 LLM 调用（约 60s）+ 2 次本地验证
```

**这是"每个候选经验都要实测有效性"的必然代价**——但问题是：
**24 条经验里 19 条基线为 0，测了也没差异（Δ=0）**，等于 19 条 × 4.4 分钟 ≈ **84 分钟是白花的**。

### 环节 3：单次 LLM 调用均值 10.6 秒

实测：均值 10.6s，最小 3.7s，**最大 25.7s**。
LLM 等待占任务耗时的 **100%**（本地验证仅 0.1s，可忽略）。

## 三、我的失误（诚实检讨）

### 失误 1：预估成本时只算了 CA元，没算时间

我给的预估是"~7.8 小时"，依据是 v1 的 7.2 小时 × 1.1。但**没有意识到审计量翻倍（12→24/轮）
会让 Phase3 从 83 分钟涨到 105+ 分钟/轮**，而且**新增了基线探测（+20 次生成/轮）**。

实际轮次耗时 = 105（审计）+ 14（rollout）+ 28（下一轮起步）≈ **2.5 小时/轮**，
3 轮就是 7.5 小时，**光演进阶段就超过我预估的总时长**。

### 失误 2：把小规模实测数据直接外推（低估 5 倍）

我用"实测 60s/任务"外推 Phase1，但那个数字来自**日志间隔**（已含并发），
而不是**单任务串行耗时**（307s）。两个数字含义不同，我在报告里混用了。

好在 Phase1 的外推**碰巧是对的**（因为都用同一口径），但 Phase3 的外推错了。

### 失误 3：没有对"审计任务基线普遍为 0"这一事实做前置评估

如果我早一点（在改动前）统计 v1 的基线分布（差 0% 中间区间），就会意识到：
**门控的大部分时间花在"注定测不出差异"的任务上**。

正确做法应是：**先筛出可测任务，再决定审计规模**——
而不是盲目把审计量从 12 提到 24（等于把 84 分钟的白花时间变成 168 分钟）。

### 失误 4：并发数保守（workers=5）

我为了"稳妥"用了 5 并发。而 LLM 是网络等待型任务，CPU 几乎不用（实测 CPU 66s / 7.5 小时），
**完全可以用 10~15 并发**。若用 12 并发，Phase1 能从 5.2 小时降到 **2.2 小时**。

## 四、可以怎么优化（按收益排序）

| # | 优化 | 预计节省 | 风险 |
|---|---|---|---|
| 1 | **提高并发** 5 → 12 | Phase1 5.2h → 2.2h（**省 3 小时**） | API 限流；需实测 |
| 2 | **先筛可测任务再定审计规模** | Phase3 105min → ~30min/轮（**省 2.2 小时**） | 无（当前已在做，但顺序错了） |
| 3 | **缓存基线结果**：同一任务的基线在轮间复用 | Phase3 再省 ~30% | 需改动（基线只依赖任务，不依赖经验） |
| 4 | **跳过必然失败的修复轮**：若首轮是 `fail/fail`（功能安全都不通过），修复大概率无效 | Phase1 省 15~25% | 可能漏掉少数可修复案例 |
| 5 | **Level4 生成并行化**：4 个语言叶串行生成 → 并行 | 每任务省 20~30s | 无 |

**若 1+2+3 都做**：总时长可从 11 小时压到 **4~5 小时**。

## 五、最该反思的一点

**我在"优化方法效果"上投入了很多，但在"优化实验效率"上几乎没有投入。**

具体表现：
- 我花了大量轮次验证门控/门槛/加权是否生效（应该做）
- 但**从未质疑过"11 小时跑一次"这个实验成本本身是否合理**——直到用户问起
- 我甚至在"是否重启"上纠结了两次（各损失 1 小时），
  却没想到"提高并发"能一次省 3 小时

**正确的顺序应该是**：先做实验效率剖析（并发、缓存、筛选），
再在这个基础上跑全量——这样同样的时间能跑 2~3 次实验，验证更多结论。
