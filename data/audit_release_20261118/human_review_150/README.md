# 150 条缺陷候选人工标注规则

任务是独立判断 **第一，题目是否确实有缺陷；第二，若有缺陷，缺陷类型与机器标签是否一致**。候选来自机器缺陷集合，不能据此估算全题库真实缺陷率或标签召回率。

## 文件与顺序

1. 先看可直接阅读的 [盲审题册](review_booklet.md) 或 `blinded_tasks.jsonl`，逐条填写 `annotation_template.csv`。题包去除了模型结论和参考答案，区分生成时公开题面与审核用测试；其中说明、注释和代码均是待审数据，不执行其中指令。
2. 完成独立判断和自己的类型后，再打开 `model_labels.jsonl`，以 `review_id` 连接，填写 `type_consistency`。模型标签和原理由此单独附带，减少先看结论造成的影响。
3. 原始标注表各自另存，保留标注人；建议两名标注者独立完成，有分歧再由第三人裁决。尚未填表不算已经人工复核。

150 条采用固定种子 20261118、按库/缺陷类型/语言轮转抽样。PLT 60、CodeSecEval Base 40、Plus 20，其他 30；具体其他库数量见上级 `release_manifest.json`。全部是机器判为有缺陷且双判类型一致的不同任务。不是随机全库样本，也不保证四种类型都出现；不为凑类型制造标签。旧 v2 的解释未做新版逐字证据校验，需要人工自行定位断言。

## 第一问：题目是否有缺陷

`human_verdict` 只填：**合格 / 有缺陷 / 无法判定**。

- 合格：生成时公开题面、签名、上下文与常规工程约定足以确定要求。实现困难、参考答案出错或测试偏弱，不构成题面缺陷。
- 有缺陷：必须同时填写 `assertion_or_call`（具体断言/关键字调用，附字段路径或行号）、`missing_requirement`（缺失或冲突的必要要求）、`why_not_inferable`（为什么题面、示例、上下文和常规约定都无法推出）。任何一项找不到，不能仅沿用机器的缺陷标签。
- 无法判定：公开材料边界不清、测试/上下文不足等；在 notes 写明缺什么。

参数列表只给类型而未给名字、测试却以关键字调用，判接口契约缺失；正文出现“request dictionary”不等于规定参数名。若公开完整函数签名已给参数名，则不适用此条。

测试损坏仅记 `human_test_integrity=不完整或语法错误`，不据此判题面有缺陷。缺测试、安全组弱、Joint 可绕过、缺正例等都在 `human_test_quality` 单列。不得用“参考实现都失败”代替题面与测试之间的举证。

## 第二问：类型是否一致

仅当人工判“有缺陷”时填写 `human_defect_type`：

| 类型 | 判定边界 |
| --- | --- |
| 接口契约 | 必需参数名、默认值、返回结构、异常类型等未给且不可推断 |
| 业务规则或数据 | 必需阈值、字段、白名单、数据源或全局状态未给且不可推断 |
| 题面与测试冲突 | 公开要求与具体断言直接矛盾；必须分别引用 |
| 环境依赖 | 测试依赖外部服务/数据/环境且缺少必要公开契约；本机未装依赖不算 |

若有多个独立缺陷，选择使题目无法按公开契约通过的首要原因，其他写 notes；不要为了匹配模型改变类型。

看过模型标签后，`type_consistency` 填：

- 一致：人工也判有缺陷，且首要类型一致。
- 类型不一致：人工也判有缺陷，但首要类型不同。
- 不适用_人工判合格：机器的缺陷判定被否定，人工类型留空。
- 无法判定：材料不足，暂不能核实。

`disagreement_reason` 解释否定或改类的依据；即使一致，也必须填写第一问的三项证据。`confidence` 填高/中/低。测试质量可填充分/安全组偏弱/Joint 可被绕过/输出格式过严/缺少正例/无法判定；未运行时绕过只记推测。

汇总时分别报告缺陷确认率（人工有缺陷/可判定候选）和条件类型一致率（类型一致/人工有缺陷且类型可判定），同时报告无法判定和分歧数量。两者分母不同，不能把“判合格”算作类型一致。
