## 二、从零解释：CLE原本要解决什么

CLE全称是 **Contrastive Lifecycle Evolution（对比式经验生命周期演化）**。它希望在不修改基座模型参数的情况下，把安全代码生成中的成功、失败和修复经验保存下来，使以后生成的代码既保留正常功能，又满足安全要求。

它的目标不是让模型“增加更多防御检查”。拒绝全部输入可能通过部分安全测试，却破坏功能；只完成业务也可能留下漏洞。因此必须同时看：

- **F（功能测试通过）**：是否完成规定的正常行为。
- **S（安全测试通过）**：是否满足给定安全测试。
- **Joint（联合通过）**：同一份代码同时满足F和S。
- **缺测**：没有足够有效测量，必须与已测失败区分。

F失败、S通过也不能一律解释为“过度防御”：覆盖外部变量、字段理解错误、接口不兼容、解析缺陷都可能产生这种结果。

### 经验卡怎样产生和组织

经验卡来自训练侧漏洞与修复代码，以及同题初次生成、修复和验证结果的对比。卡片应保留错误原因、修复动作、适用前提、排除条件和功能保持约束，而不是复制答案常量。

HSK Tree（按安全知识分层组织经验的树）在根节点以下分为：CWE类别、安全不变量簇、正向原则与负向护栏。语言和API提示保存在卡字段中，不额外构成树层。统一经验池还保留来源、状态和失败记录。

当前1939张卡不等于1939条独立验证正确的规则。provisional表示待验证；允许被试用不等于已晋升。卡片被合并、访问或获得正奖励，也都不能直接当成独立证据数。

### P7是什么

P7（旧CLE完整单题解题流程）包括：初次分析、候选召回、LLM（大语言模型）选卡、经验复析与采用、规划、代码生成、F/S验证。初次代码记为c0；若未Joint，最多进行一次修复c1，最终成绩来自交付的末次代码。

“共享初析”主要控制首轮输入。修复查询包含各臂自己的代码和反馈，后续路径会自然分叉。因此首轮输入相同，不表示整条轨迹只有一个变化因素。

**本轮Q扩展固定卡正文和生命周期，仅更新Q与访问计数，没有完整执行原CLE的卡片生成、晋升、合并、退役闭环。** Q专项结束与整个CLE项目完成必须分别记录。

## 三、实际Q实现：它与MemRL的关键差别

### 1. 当前Q改变的是呈现顺序，最终记忆仍由模型决定

04中的实际调用路径是：

- 按语言、生命周期等条件确定可用卡。
- 取余弦相似度前24张，加词语重合前8张，合并去重，最多32张候选。
- 在本次候选集合内计算：
$s_i=0.5\,z(\text{cosine}_i)+0.5\,z(Q_i)$

其中 $z$ 是候选集合内的标准化值；某通道没有方差时，该通道全部记零。

- **重排完整候选集合。** 当前调用使用limit=None，并非数值上直接截取前三张。
- LLM阅读卡正文和临时候选编号，选择零至三张；后续复析还可以拒绝部分卡。

选择器看不到Q数值。顺序变化也会改变临时编号。因此这是“Q影响呈现，再影响模型选择与采用”的间接机制。旧代码中存在数值直接选前三张的辅助路径，但不能用它描述当前在线实验。

当前 $\delta=-1$ 且要求余弦值严格大于它，几乎不提供有意义的绝对相似度门槛；不过前24加前8的召回仍构成候选过滤，不能说系统完全没有语义筛选。

### 2. 更新规则与更新时点

对有效、完整测量的代码：

$r=\begin{cases}
+1,&F=1且S=1\\
-1,&其他完整测量结果
\end{cases},
\qquad
Q_{\text{new}}=0.7Q_{\text{old}}+0.3r$

只有声明采用且满足授信条件的卡获得更新。缺测、空代码、规定的不完整流程等不授信。

**当前在线实现是真正的参与式学习：一题P7内部的Q保持不变；保存该题轨迹后，依次处理c0、c1奖励；下一题看到更新后的Q。** 它不是“本题c0失败后立即用新Q选择c1”。

### 3. 与MemRL的精确对照

本次核对了所附MemRL论文及其arXiv v2原文。论文研究的是冻结模型参数、通过反馈更新外部情景记忆的效用。[arxiv.org](https://arxiv.org/html/2601.03192v2?utm_source=chatgpt.com)

| 方面 | MemRL原文 | 当前CLE扩展 |
| --- | --- | --- |
| 记忆内容 | 意图—经验—效用三元组 | 安全原则、护栏、错误原因等固定卡片 |
| 最终选择 | 先语义筛选，再按组合分数直接选最终top-$k_2$记忆 | 组合分数只重排，再交LLM选卡和复析采用 |
| 记忆增长 | 运行后写入新经验摘要 | 本专项不生成新卡、不改正文或生命周期 |
| 相似度门槛 | 论文表8按任务设置约0.25–0.62 | 当前为−1 |
| 效用更新 | EMA（指数移动平均）式反馈更新 | 使用同类更新，学习率0.3 |
| 多记忆归因 | 原文也承认共同回报带来的授信困难 | 整份代码结果分给声明采用卡，问题仍在 |
| 评测含义 | 区分运行中学习与冻结后的迁移 | 当前303题是在线轨迹，最终967/972状态尚未得到新冻结评测 |

所以这是**对MemRL思想的具体迁移与改造，不是完整复现**；也不能把它写成原创的Q更新算法。论文自身的收益、训练轮数或累计成功率，不能直接作为CLE“必须多跑几轮”的理由。

## 六、实际代码审阅：真正影响决策的问题

### 1. 共享奖励衡量的是整条尝试表现，不是单卡真理

当前每张声明采用卡收到相同整段代码奖励。由此：

- 正确建议可能因为模型没有落实、或其他代码错误而被扣分。
- 无关卡可能搭乘一次成功得到正分。
- 多卡共同使用时，无法从同一回报识别各自贡献。

这不是EMA算术写错，也不是MemRL独有的问题；它意味着Q估计的是“在当前生成器和共同上下文下，被采用后出现的结果关联”，而不是“这条规则自身正确的概率”。

c0/c1的重复授信还改变了目标：同卡经历c0失败、c1成功后，

$Q'=0.49Q+0.09$

而首轮成功为 $Q'=0.7Q+0.3$。修复成功与直接成功并不等价；访问次数也不是独立任务数。

### 2. 低支持Q可以造成明显排序，但不能据此断言每次改选有害

相似度相同时，冷卡 $Q=0$ 会排在负Q卡之前。冷卡是没有测量，不是已经证明更好。当前评分也没有使用访问数表达不确定性。

此外，候选内标准化会放大相对差异：把所有Q乘一个正数不改变其标准化结果，所以很小、支持稀疏的Q差别也可能产生明显顺序变化。

这些是代码可确认的机制。**“冷卡替换负Q卡造成多少损失”仍需实际曝光记录支持，不能由公式直接推断。** 同一标量跨多个业务family使用，也可能混合完全不同的适用条件；但目前没有把跨family负迁移从生成噪声和契约错误中单独识别出来。

### 3. 全库覆盖不是实际曝光覆盖

当前972/1939＝50.13%，只表示“至少获得过一次有效授信”的卡占比，不表示半数卡已被可靠验证。

旧M1全库覆盖只有24.03%，但旧D_gate Q2的选入出现中55.57%来自有Q卡，声明采用出现中61.22%来自有Q卡。**因此不能说旧研究因76%的卡未学过，Q几乎没有实际曝光。**

不限量D_init的新卡漏斗是687进入候选、447被选、277被采用、257获得有效反馈。未学习卡可能根本没被召回，也可能不适用、未采用或没有有效奖励。增加轮数不会保证这些瓶颈消失。

最新836次D_init有效更新中297正、539负；D_grow的66次中21正、45负。这些是“卡—尝试”事件，不是独立题目。覆盖增长与收益增长没有数学上的必然关系。

### 4. Q3保留类内分布，不保留真实支持与曝光

同CWE置换保留分配后的Q、visits分布，但某张卡拿到的访问数可能属于另一张卡。必须分别记录“被分配的访问状态”与“该卡真实历史支持”，以及候选、选入、采用各层的曝光。

这不使置换对照自动无效；它仍是特定Q映射的对照。但它不能保证上下文暴露分布相同，也不是所有可能置换的充分抽样。因此Q2与一次Q3接近，不能推出“学习Q完全没有信息”。

### 5. 顺序、重复与恢复需要正确解释

温度0没有消除实际观察到的选择波动。当前在线学习串行推进，Q又受任务顺序和近期奖励影响；它不是对一个固定政策抽取303个相互独立样本。

恢复代码从固定阶段起点重放已保存前缀，结构上支持避免重复授信；不能无证据指控当前恢复必然双重更新。但未知请求用量仍须单列。

旧“新增卡数达到6/3即可扩张”的门只检验能否产生反馈，不检验收益。当前在线协议则明确没有性能续跑门。代码有调用和Token停止预算，不能再批评为完全无预算；但**程序允许继续，不构成科学上值得继续的理由**。

### 6. 清洁Q回放能回答什么

同一初始状态、同一事件序列的精确回放，可以核对Q账本。过滤失格事件后的回放，可以做**历史授信敏感性分析**。

但当前学习本身受Q影响：早期Q改变，后续选卡、代码和回报就可能改变。所以过滤旧事件并重算Q，**不是重建“如果从一开始使用清洁Q会发生什么”的学习轨迹**。

同样，不能把新Q排序套到旧结果上，宣布新政策Joint。旧代码属于旧决策过程；要测新的生成政策，必须实际产生对应代码与验证证据。相同提示的旧结果最多是该输入的一次已有观测，不是新增试验。

### 2. 正例中也有真实修复，以及不能夸大的“通过”

20个救回中存在具体代码改善：

- 1174旧代码把集合用作isinstance第二参数，存在类型错误；新实现消除了这一结构问题。
- 1382旧AST（抽象语法树）验证把操作符节点也当成非法节点；新实现修正递归方式。
- 834旧逻辑逐个扫描单词，却与多词字符串ORDER BY比较；新解析方式改正了这一缺陷。
- 多个正例保留了原先被清空的外部数据库或模板。

这些不能全部贬为噪声，但也没有逐例建立Q因果链。1113虽选了三卡却声明采用零卡，仍救回；1150首轮卡成员和顺序与旧组相同，旧组无代码，新组通过。它们不能统称“新增卡生效”。

反过来，1063和999的新通过代码仍硬编码外部配置，只是更贴近当前测试。**通过现有F/S不等于完整契约语义都正确。**

### 3. 一个独立发现：907的旧通过代码也暴露验证缺口

907的测试预置：

```python
from queue import Queue
task_queue = Queue()
```

旧Joint通过代码和新代码却都将其替换为task_queue=[]，使用列表的len与append。所附测试只检查返回布尔值，没有验证原共享Queue是否被正确写入。

这意味着旧F通过不能证明实现了题意中的共享队列操作；也意味着“一律删除全局赋值”不是可靠通用修补，删除后列表操作与Queue接口仍不兼容。

1037、989的字段信息，以及874、907的资源阈值，也提示必须区分：**明确违反公开契约的模型错误，和公开契约不足以确定测试预期的数据问题。**
