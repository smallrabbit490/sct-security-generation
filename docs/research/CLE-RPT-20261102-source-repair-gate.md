# 来源题先验证修法，能否挡住错误经验并提高 Joint？

**实验原型挡住了第 356 题派生出的三张错误指导卡；第 1290 题最终 Joint 仍为 0/2。** 原卡也是 0/2，救回 0、损失 0。这条门槛在本例能够阻止错误建议进入生成，尚未产生新的有效修法。停止在第 1290 题上继续做过滤扩样。

## 规则怎样执行？

在把一种修法作为可推荐动作前，先在同一来源题、同一验证器上验证整份补丁。来源题原本未通过 Joint，补丁后功能与安全均通过，才支持推荐这份修复。出现退步、修后仍失败或存在未测，均保留失败记录，不把它作为已验证修法。来源题原本就通过时，前后都通过也不计作一次新修复。

这个判定确认整份补丁组合在来源题上的效果。补丁包含多处改动时，不据此说某一行是唯一原因；跨题收益由后续同题对照测量。

现有 CLE 会把失败轨迹中的盲区、最小修法和过度防御提醒分别转成独立卡片入池。第 1290 题实际选中的三张卡均来自 356，均含改算普通摘要的建议。新增原型位于 `methods/sct_trajectory/source_repair_evidence.py`，在本轮研究副本中决定哪些内容能进入推荐卡列表。原卡完整保存在失败记录中，正式库与活动执行流程没有改动。

## 本次具体做了哪些验证？

1. **反例。** 复用第 356 题公开题面及参考实现，只把带密钥的计算换成对消息直接求摘要。功能由通过变为失败，安全仍通过。三张卡共享这一建议，实验副本将三张都移到失败记录，推荐列表为空。这里使用来源题参考实现构造局部反例；未把它冒充为当初生成三张旧卡的完整历史轨迹。
2. **正向检查。** 将上一轮已经定位的 1018、1021、1027、1364、835 五条真实来源修复轨迹逐份回放，十份代码的功能与安全结果均与保存记录一致。五条轨迹均从功能失败、安全通过变为 Joint 通过，门槛保留五份修复组合。它们是预先已知成功的检查材料，不能用 5/5 估计未知卡的合格率。
3. **边界检查。** 五项定向测试覆盖真实修复、功能安全间的退步、未改善或部分改善、未测和原本就通过，全部通过。
4. **目标题比较。** 第 1290 题过滤后的三张卡全部被排除。对第 1、2 次原初析分别运行原生 P7，逐字核对每个请求与已保存的无卡请求一致，复用全部十四次成功响应，再用原验证器评分。代码、两轮功能和安全结果均与旧记录一致，没有新增模型或 Embedding 请求。

## 对提炼主线意味着什么？

这次证据支持把“来源上验证过的修法”和“失败后猜测的修法”分开使用。失败记录仍有研究价值，但本例中的“移除带密钥计算”不能继续作为成功操作建议。

本例也表明，撤掉错误指导以后，生成模型仍可能自行设置替代密钥，继续功能失败。要提高 Joint，需要形成并验证新的正确修法，再从成功的来源轨迹提炼经验；给旧建议加限制或单纯删除旧建议，均未在 1290 上取得收益。提炼规则的后续比较应检验这一步，而不是继续调整本题卡片措辞。
