## 2. 多卡共同奖惩是普遍操作，不能直接当单卡质量

327/403次（81.14%）共同采用多卡，贡献826/902次（91.57%）更新。同次所有卡取得相同奖励，不能由这份账本推断哪张造成失败。上述比例描述信用分配的结构，不是“错误奖惩率”。

另有9个修复前后代码完全相同的题对；其中12条卡片负更新再次落在同一代码、同一张卡上。1003就在其中。原规则允许按尝试更新，因此不将它写成实现bug；但这些更新不是新增独立题证据。两次相同奖励的有效权重为`Q₂=0.49Q₀+0.51r`，比一次的0.3更快压低/提高Q。

三个新版本都保留了部分安全动作，却把实际业务对象替换了。安全分高不能修复被清空的业务输入。诊断证明这些代码违反具体公开绑定，不证明记忆或Q导致了重定义；历史两次运行的状态、时段与修复输入不同。

### 1003：为什么不能简单说“低Q说明这张卡没用”

`hint-79-4223192076816222301`明确要求删除硬编码模板、使用外部模板；首次与修复代码却都包含：

```python
USER_POST_FORMAT = ('<div class="user-post">' ...)
```

该卡两次实际采用，Q从−0.564804393降至−0.6953630751，再降至−0.78675415257。两份代码完全相同。另两张分别在首次/修复采用的blind卡，也明确反对硬编码或替换模板。至少4条更新中，可以核对到这条保留要求未被落实却获得负奖。

这不等于认证这些卡全部建议都正确：同次另一张`hint-79-3803396337429303372`建议增加模板参数或导入常量，含有需要另审的接口适配前提。不能把整张卡、整次失败统一标成“好卡”或“坏卡”。

642末次只采用1张卡仍失败，说明即使去掉多卡共同奖惩，消费者违反公开配置的问题也可能存在；“单卡更新”本身不足以解决归因。

### 1113：出现救回，也未必经过Q采用路径

1113新侧首次Joint通过，`applied_ids=[]`；旧侧交付失败。两份代码还存在DNS校验、IP处理、导入等多项差异。不能仅看到救回就归为Q功劳，也不把新增`import re`直接认定为唯一原因，因为公开环境本就提供`re`。本例缺少可核对的“Q改选—接受卡—落实—救回”链。

## 4. 同CWE不同题族反馈相反，现象是否存在

463张本轮获反馈卡中，58张在不同family出现相反的纯方向反馈；限同CWE后为55张（占463张的11.88%）。这里“纯方向”仅指当前可见记录中，该族全为+1或全为−1，不表示已经收敛。另8张卡在同一family内部就有正负不一致。

- 22张：来源family当前为正，至少另一同CWE family为负。
- 15张：来源family当前为负，至少另一同CWE family为正。
- 其余相反组合不一定包含来源family。上述两类与55张的关系不是把22、15再与55相加。

例如`cand-327-8553196517194194335`来自题373，当前10次更新、5正5负，覆盖9个family。它展示单个Q混合了不同任务反馈；尚未逐族确认是前提不适用、实现错误或波动，不能据此自动启用条件Q。既有条件Q门未过的决定保持。

## 5. 为什么这轮反馈很多，覆盖率只增加一点

实际输入快照中已有926/1939张获得过反馈，当前972/1939张；新增覆盖46张，即47.76%→50.13%，增加2.37个百分点。

本轮获反馈的463张中，417张此前已经访问过（90.06%），46张是首次获得反馈。463不是新增463张；972也不意味着这些卡都在本轮学过。另509张本轮没有新反馈，但保留更早学习的Q。

这支持“曝光集中在已学卡”的描述。它不证明应该强制让所有卡获分：没被实际采用的卡缺少当前实现证据，直接给分会改变原研究对象。提高覆盖率不能代替选卡和下游Joint验证。
