# 第一步补充：为什么"换检索机制"不改变结果 —— 根因取证

日期：2026-09-22
背景：第一步的消融显示，`hier_llm` 与 `flat_llm` 的 JointPass 完全相同（配对 +0.0pt）。
本文记录对"注入的经验到底有没有起作用"的取证结论。

---

## 一、结论先说：原假设被**证伪**

我最初的假设是"注入的经验没有真正影响生成的代码"。**取证结果否定了这个假设。**

| 问题 | 结论 | 证据 |
|---|---|---|
| 经验有没有进入提示词？ | **有** | `agent_pipeline.py:313`（Planning）/`:361`（CodeGen）渲染 `dual_track_text(cards)` |
| 失败现场字段有没有渲染？ | **有** | 专门区块【失败现场·来自真实动态测试】，含"· 建议修法（可直接照做）：" |
| 换经验会不会改变代码？ | **会** | 54/54 任务的注入 id 不同；生成代码**逐字节相同的有 0/54** |
| 那为什么 JointPass 一样？ | **状态变化互相抵消** | 13/54 任务状态变化（hier 把 1126 从 C 提到 A，同时把 1388 从 A 打到 D） |

**→ 注入是有效的；问题在"载荷"（directive）的质量，不在注入通道。**

---

## 二、载荷的三个具体缺陷（均已独立核实）

### 缺陷 1：所有经验都以"仅供参考"的口吻给出 —— 没有任何硬约束

```
constraint_type 的写入点全仓只有 1 处：
    experience_filter.py:127   enriched["constraint_type"] = a["type"]

而 filter_experiences 的默认值是 False
→ experience_filter 不跑 → constraint_type 从不被设置
→ dual_track_text 只能落到两个分支：
      【软建议·仅供参考，不得为满足它而破坏功能】  (106/219)
      【负向红线·务必避免】                      (113/219)
      【硬不变量·必须满足】                        (0/219)   ← 一条都没有
```

**含义**：模型收到的每一条经验都被明确告知"仅供参考"。这与方法的意图
（安全不变量本应是必须满足的约束）直接冲突。

### 缺陷 2：指令被截断，尾部到不了模型

```
agent_pipeline.dual_track_text 的渲染上限：
    root_cause      → 400 字
    fix_directive   → 400 字
    prev_fix_assessment → 300 字

经验池实测：
    含 fix_directive 4305 条，最长 2101 字
    超过 400 字的 354 条（8%）→ 尾部指令被丢弃
    被注入的 219 条里 31 条超限（注入偏向长文本，比例更高）
```

### 缺陷 3：多轮指令用「——」拼接，可能自相矛盾

```
_merge_text 的拼接方式： old_s + "\n——\n" + new_s，再按 limit 截断

经验池实测：含「——」的 fix_directive 122/4305（3%）
    拼接段数分布：2 段 84 条、3 段 11 条、8 段 10 条、7 段 5 条 …

取证抽样（108 条被注入记录）中发现 9 条自相矛盾，其中 8 条是**同一张卡片内部**矛盾：
    例：同一节点既写"先对原始输入进行空字节检查（若含 '\x00' 则返回 False）"
        又写"完全移除空字节检查（因契约未要求）"
    例：同一节点既写"删除所有类型检查与强制转换"
        又写"先使用 str() 强制转换为字符串"
```

**含义**：模型面对同一张卡片里的两条相反指令，只能二选一，等于随机。

### 附带缺陷 4：成功经验被贴到"失败现场"标题下

`direct_A`（一次通过范例）卡片的 `root_cause` 文本是"【安全测试通过，无失败】"，
却被渲染在【失败现场·来自真实动态测试】区块里 —— 语义标签与实际内容矛盾。

## 三、其它已核实的事实

- **指令确实会被遵循**：抽样 10 个任务，4 YES / 5 PARTIAL / 1 NO。
  YES 的案例近乎逐字照做（`max_iterations = 10`、`urllib.parse.unquote_to_bytes`、
  `errors='replace'`、`def process_json_input(request: Request)` + 类型检查）。
  **但 4 个 YES 里有 2 个最终仍是状态 D** —— 忠实执行指令并不保证通过。
- **没有任何 `kind` 有显著效果**：按 CWE 标准化后，`direct_A` 的边际优势
  +20.5pt 塌缩成 期望 9.67 vs 观测 10（+0.33）；41 个分层里 4 好 / 7 坏 / 30 平。
- **两处运行质量混淆**（下次实验必须先排除）：
  - `flat_llm` 臂记录 59 次 API 错误，`hier_llm` 臂 0 次；
  - `hier_llm` 臂 3 个任务因 `model_output_truncated`（max_tokens=1500）计为 D，
    把它的 D 从 11 抬到 21、分母缩到 51。

## 四、对后续步骤的修正

| 原计划 | 修正后 |
|---|---|
| 第二步：比哪个阶段的池更好 | **仍可做**，但先修载荷缺陷，否则比较的是"有缺陷的载荷"之间的差异 |
| 第三步：提高门控覆盖率 | **前提变了**：门控要筛的不只是"经验对不对"，还要筛"指令是否自洽、是否够短、是否该当硬约束" |

**重设计方向（按收益排序）**：
1. **让安全不变量真的成为硬约束** —— 打开 `filter_experiences` 或直接在
   `dual_track_text` 里按 `kind` 判定约束强度（不依赖 experience_filter）。
2. **不再截断指令**（或把上限提到覆盖 P95），必要时拆成多条卡片分别渲染。
3. **合并/去重多轮 `fix_directive`**，消除同卡内部矛盾。
4. **修 `direct_A` 的标签**：成功范例不应挂在"失败现场"标题下。
5. **缩小 `negative_guardrail` 的巨型拼接块**（实测可达约 4000 字）。
