# 在正常 CLE 流程中，用来源修复验证过的动作写卡，能让新题多过几道？

后续已完成[失败复盘与迭代后的零 API 回放](CLE-RPT-20261103-completeness-repair-v02.md)。公开修复救回 4 份已测失败、涉及 2 族，另 1 份恢复测量后通过。以下保留模型原始成绩。

**结论：这次改卡让三份代码多通过了功能测试，最终 Joint 没有增加。原生、来源验证、公开规则三组各有两份代码达到 Joint，全部来自密码题。来源验证组对原生组和公开规则组分别有 11 个可比配对，均为救回 0、损失 0。保留原生提炼为默认，不扩大本版。**

这批比较只换经验库。模型先读公开题面，自行检索、选卡和决定是否采用，再生成代码；首次失败最多修复一次。每组运行相同的六道题，每道题独立重复两次。主结果是交付代码同时通过功能与安全测试的次数（Joint）。同题同一次重复，一组通过、另一组失败，才算一次救回或损失。

三组使用相同背景卡及相同卡位。**原生组**保留 CLE 原提炼出的卡；**来源验证组**只在来源修复能验证“保留现有外部对象”这个动作时替换原建议；**公开规则组**直接依照公开条件写同一句动作。后两组只在 1027 号卡有区别：来源验证组保留原授权建议，公开规则组换成保留外部对象的建议。这一设计能检验新卡如何影响整条自然流程，以及来源验证是否比直接写通用规则多带来收益。

六个题族在查看本次结果前锁定。它们未参与本规则设计，均曾进入历史功能与安全实验，属于库内探针。比较采用全部分配单元，未选到卡或声明拒用的单元继续计入各组分母。[事前方案与扩大门槛](CLE-PLAN-20261103-distillation-completeness.md) · [来源阶段证据](CLE-RPT-20261103-distillation-completeness.md)。

## 功能改善有多大？能否解释为 Joint 提升？

36 个固定生成单元全部交付，原生流程零付费回放 36/36 一致。共 35 份最终代码得到功能、安全两项测量。表中通过率的分母只含实测代码。

|提炼方式|交付／最终实测|功能通过|安全通过|最终 Joint|首轮 Joint|使用一次修复|
|---|---:|---:|---:|---:|---:|---:|
|原生提炼|12／12|5/12|5/12|2/12（16.7%）|2|10|
|来源验证后写卡|12／11|8/11|4/11|2/11（18.2%）|2|10|
|只按公开条件写规则|12／12|6/12|4/12|2/12（16.7%）|1|11|

**18.2% 与 16.7% 的差来自分母。** 在同题同重复的 11 个可比配对中，三组各有 2 个 Joint。来源验证组对原生组的两次重复净增分别为 0、0；对公开规则组也是 0、0。按可比配对分题族重抽样，六族观测到的 Joint 差都为零，区间因此退化为 [0,0]，两项探索性 Holm 校正值均为 1。这描述本批观测，不能据此宣布其他题族等效。

相比原生提炼，来源验证组净多通过 **3 次功能测试**：签名题第一次、文档题两次；其余 8 个可比配对无功能变化，11 个可比配对无安全变化。相比公开规则组，来源验证组也多通过 3 次功能测试；安全方面，转账题第二次多通过一次，队列题第一次少通过一次。三组有完整两次实测的题族分别为 6、5、6 个，组内这些题族的最终 Joint 在两次重复间均未翻转。

唯一未测的是来源验证组队列题第二次的修复输出：一行 Python 同时用了集合与字典写法，语法检查失败，两项动态测试没有运行。只移除这个未使用的赋值，原验证器回放即通过 Joint；这份事后修正不是正式交付。即使给缺测取最有利结果，最终净救回也只能在 **0 至 1** 之间，达不到预定的至少 3 次、覆盖至少 2 个受益族的门槛。两种对照都不支持扩大。

## 新卡改变了代码的哪一步？

在被替换的三个卡位中，原生组 5/12 个单元曾选中、1/12 个曾声明采用；来源验证组与公开规则组均为 8/12 个选中、8/12 个采用。在四个需要外部对象的题族中，最终能解析的代码里，直接在模块顶层重新赋值的次数为原生 **4/8**、来源验证 **1/7**、公开规则 **4/8**；候选还有一份无法解析，不记作“避免了重建”。这个计数仅指无条件顶层赋值；条件中的后备对象和对既有对象调用错误方法另读代码判断。

来源验证组保留了 1027 的原授权建议，公开规则组改写了它。这张直接区分两库的卡，在来源验证组 4/12 个单元曾选中、0/12 个采用；在公开规则组 3/12 个选中、2/12 个采用。因此可以说候选改变了选卡、采用和部分公开任务的实现；不能把功能收益单独归因于 1027 的内容，也不能声称来源验证带来了通用规则没有的 Joint 收益。

## 怎样判断失败与卡片有没有关系？

这批已经核实三种不同的情况。文档题的一次运行在修复时把原文档表重置为空；同一份代码还用错误字符串拒绝越权请求。只移除重置，功能通过、安全失败；只把字符串换成权限异常，原表仍然为空，两项均失败；两处都改才通过 Joint。代码中同时存在两种错误，不能把全部失败归给一张卡。

签名题的公开说明要求对未知编号抛出异常，安全测试却要求返回 `False`。转账题只要求返回成功消息，功能测试逐字比较指定英文句子。在两份已经落盘的代码上，只按测试更改相应行为即可救回 Joint。这样的本地改动用于解释测量，没有加入任何卡片或模型提示，也不改变正式成绩。

队列题检验普通任务能否入队、超大任务会不会被拒绝，但不检查调用方给定的队列是否真的收到任务。逐份阅读代码发现，原生组第一次和公开规则组第二次都重新创建了队列，却仍能通过普通任务测试。因此仅看该测试无法判断是否保留了调用方的队列。

## 这条研究线保留什么，停在哪里？

保留“只把来源代码能验证的修复动作写进卡”作为来源提炼候选：三轮增长轨迹中有 4 条修复、来自 3 个来源族，通过了删除、还原和无关改名对照。本批把它接回自然检索后，观察到功能收益，却没有得到最终 Joint 收益，故不更新正式卡库。下次重新考虑这条线需要新证据：从其他训练来源自然提炼出**既保留调用方对象，又使用它公开支持的操作**的可执行建议，并在未参与设计的题族上同时胜过原生和公开规则。不得把此次从目标题测试学到的数值、文案或接口名抄回卡中，再用同题验证。

模型固定为不带 1017 的 `deepseek-v4.1-flash`。311 次模型请求已报告 1,501,121 Token；45 次向量请求已报告 62,676 Token，另有 1 次未知用量按 2,476 Token 预留。**已知合计 1,563,797，含未知的预算占用 1,566,273／1,800,000。** 两次恢复分别复用了保存的初析和 12 个已完成单元；一次服务端成功返回的初析带有 JSON 注释，沿用原生降级且没有重抽。统计、逐题诊断及交付回放均未调用模型。本批没有启动排队全量。
