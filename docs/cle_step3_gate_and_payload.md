# 第三步：门控覆盖与成本 —— 设计前的实测与载荷修复

日期：2026-09-22
目标（用户要求）：设计并实现"门控覆盖率尽可能高、成本不显著上升"的方案。
现状：门控只覆盖 72/4518 = 1.6%，晋升 13 条 active。

---

## 一、先量化：门控要审的候选里有多少是"有缺陷的载荷"

对 `cle_full_874_20260922` 的 4518 条经验做静态体检：

| 检查项 | 命中 | 占比 |
|---|---|---|
| `fix_directive` 超 400 字（会被静默截断） | 354 | 8.2% |
| `root_cause` 超 400 字 | 329 | 7.6% |
| 无任何失败现场（rc/fd/pv 全空） | 204 | 4.5% |
| `fix_directive` 含「——」多轮拼接（可能自相矛盾） | 122 | 2.7% |
| 指令过短（<30 字） | 3 | 0.1% |
| **被标记为「载荷可疑」（去重后）** | **800** | **18%** |

**去重不是机会**：池内精确重复仅 1 条、近似重复（Jaccard≥0.6）仅 5 对
——现有的 `_absorb_in_pool` 去重已经生效。

**含义**：静态质检只能把候选池从 4518 降到 3718（**1.2 倍预算放大**），
不足以单独解决覆盖率问题。真正的瓶颈不在"候选太多"，而在**载荷本身有缺陷**。

## 二、载荷修复（已实现，369 tests passed）

按第一步取证的四个缺陷逐条修 `agent_pipeline.dual_track_text`：

### 修复 1：约束强度按 `kind` 判定（缺陷1）

```
原状：constraint_type 只由 experience_filter.py:127 设置，
      而 filter_experiences 默认 False → 实测 0/219 条渲染成【硬不变量】，
      全部降级为"仅供参考"，与"安全不变量必须满足"的方法意图冲突。

修法：显式 constraint_type 优先；缺失时按 kind 兜底：
      已证实正确（direct_A / *_to_A / seed_from_diff）→ 【硬不变量·必须满足】
      minimal_patch_hint                            → 【推荐手法·优先采用】
      陷阱/停滞/失败/退化                            → 【负向红线·务必避免】
```

### 修复 2：不再静默截断（缺陷2）
上限 400 → 1200 字，且截断处显式追加"……（原文过长，此处已截断）"，
避免模型把残句当完整指令。

### 修复 3：多轮拼接拆段、以最新为准（缺陷3）
`——` 拼接的指令拆成段，去掉重复段，**最后一段作为最新指令**，
更早的标注为"（历史轮次的改法，可能已被取代：…）"，
消除"同一张卡片里两条相反指令、模型只能随机二选一"的问题。

### 修复 4：成功范例不再挂"失败现场"标题（缺陷4）
`direct_A` 的 `root_cause` 是"【安全测试通过，无失败】"，
改渲染在【已证实做法·来自通过样本】下，标签与内容一致。

新增 5 项测试锁住这些行为（`tests/test_agent_pipeline.py`）。

## 三、修复暴露出的关键差异：两个臂注入的经验**类型构成完全不同**

| 臂 | 去重后卡片 | 【硬不变量】(已证实正确) | 【推荐手法】 | 【负向红线】 |
|---|---|---|---|---|
| `flat_llm` | 113 | **0（0.0%）** | 26（23.0%） | 87（77.0%） |
| **`hier_llm`** | 130 | **41（31.5%）** | 47（36.2%） | 42（32.3%） |

- `flat_llm` 注入的 113 张卡片里**没有一张**是"已证实正确"类，
  77% 是"别这样做"的警告 —— 只告诉模型**不要做什么**，没告诉它**该做什么**。
- `hier_llm` 会注入 `direct_A`(26) 与 `seed_from_diff`(15)，
  因此**载荷修复后**它才第一次能产出【硬不变量】。

**这解释了为什么第一步的消融里两个臂 JointPass 完全相同**：
修复前**所有**卡片都被渲染成"仅供参考"，硬约束一条都没有，
两个臂的载荷在模型眼里是同一类东西 → 差异被抹平。

## 四、对第三步门控设计的影响

原目标"提高门控覆盖率"的前提需要修正。三层含义：

1. **覆盖率不是主要矛盾**：静态质检只能放大 1.2 倍预算；
   而"审了 1.6%"之所以无效，是因为**被审的对象本身有系统缺陷**
   （0% 硬约束、8.2% 被截断、2.7% 自相矛盾）。
2. **门控应新增"载荷质量"维度**：除了现有的 ΔJointPass（昂贵），
   先用零成本规则筛掉"载荷可疑"的 18%，再把预算花在剩下的 82% 上。
3. **更根本的是先修载荷**（已做），否则门控选得再准，
   注入的东西在模型眼里仍然只是"仅供参考的建议"。

### 建议的门控形态（三级，待实现与验证）

```
Tier A  载荷静态质检（零 LLM 成本，覆盖 100%）
        规则：截断风险 / 拼接矛盾 / 缺失失败现场 / 指令过短
        产出：payload_quality 标记（不淘汰，只排序与降权）

Tier B  约束强度标注（零 LLM 成本，覆盖 100%）
        按 kind 给 hard / soft / negative（已随修复1落地）

Tier C  动态有效性门控（昂贵，只审 Tier A 未标记的 82%）
        现有 ΔJointPass；按 payload_quality 降序消耗预算
```

## 六、Tier A 静态筛选器：已实现，但覆盖率收益有限

新增 `methods/sct_trajectory/payload_quality.py`（零 LLM 成本，覆盖 100%）：
按载荷缺陷打分与排序，把"注定读不到"的候选排到最后。

**在真实池（4518 条）上的实测**：

```
可用   4279 条（94.7%）
不可用  239 条（5.3%）

标记分布：
    no_failure_evidence     204
    multi_round_concat      122
    root_cause_truncated     44
    directive_truncated      35
    possible_contradiction   35   ← 直接判不可用
    prev_fix_truncated        3
    guardrail_bloated         2

→ 门控若只审可用候选，同等预算覆盖率仅提升 1.06 倍
```

**结论：静态筛选解决不了覆盖率问题。** 虽然 18% 的条目"载荷可疑"，
但其中大多数只是"会截断"或"多轮拼接"，仍然可用（只该降权）；
真正不可用的只有 5.3%（239 条）。

**7 项测试**（`tests/test_payload_quality.py`）锁住评分行为；
阈值 `MIN_DIRECTIVE_LEN=20` 用真实数据校准（实测最短 21 字、P1=65 字）。

## 七、第三步的诚实结论与遗留问题

### 已交付
1. **载荷缺陷量化**：18% 可疑、5.3% 不可用、去重无空间（仅 5 对近似重复）
2. **载荷修复**（4 项，见第二节），369→376 tests passed
3. **Tier A 静态评分器**（`payload_quality.py` + 7 项测试）

### 未能达成
**"门控覆盖率尽可能高、成本不显著上升"这一目标没有可实现的方案**，原因：
- 静态筛选只放大 **1.06 倍**预算；
- 动态门控（ΔJointPass）的成本与"经验数 × 任务数 × 2"线性相关，
  在不增加预算的前提下无法显著提高覆盖率；
- **更根本的是**：四轮实验一致表明，**提高覆盖率不会提升通过率**——
  检索机制、池阶段、池规模、载荷质量全部改动过，JointPass 纹丝不动。

### 遗留的核心问题（建议作为下一步）
剩下的解释只剩两条：

| # | 解释 | 如何验证 |
|---|---|---|
| **1** | **任务难度地板**：44% 任务任何配置都做不对；可解任务的失败源于模型能力，而非缺知识 | 已部分证实（24/54 任务四臂全 0）。可测：给出**官方参考补丁**后通过率是否上升——若也不上升，则是能力天花板 |
| **2** | **经验内容不够针对**：`fix_directive` 是"通用手法"，模型仍需自己落到具体代码 | 可测：注入**同一任务上一轮的具体报错 + 具体改法**（同任务历史经验），对比通用手法 |

**建议下一步做这两个实验**，它们能决定"经验注入"这条路是否还有价值。
