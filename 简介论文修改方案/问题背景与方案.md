# 组会问题的项目背景与方案

## 1. CodeSecEval Base/Plus 的 Python 测试缩进问题

### 当前项目情况

需要检查的文件是：

```text
data/SecEvoBasePlus/Base/Python_Base.json
data/SecEvoBasePlus/Plus/Python_Plus.json
```

检查对象是每条记录中的 `Test`、`Test-FP` 和 `Test-SP`。

当前已经发现：

| 文件 | 字段 | 检查结果 |
|---|---|---:|
| Python_Base.json | Test | 115 条中 1 条存在语法错误 |
| Python_Base.json | Test-FP | 115 条均可解析 |
| Python_Base.json | Test-SP | 115 条均可解析 |
| Python_Plus.json | Test | 140 条均可解析 |
| Python_Plus.json | Test-FP | 68 条存在缩进错误 |
| Python_Plus.json | Test-SP | 140 条存在缩进错误 |

典型错误是 `def check(candidate):` 后面的测试语句没有缩进，或者 `try:` 后面的语句没有缩进。这会导致评测器在执行测试前就报 `IndentationError`，从而无法判断模型生成的代码是否正确。

### 处理方案

建立三份结果：原始数据集保持不变；修复后的运行版本只修复确定的格式问题；修复清单记录任务 ID、字段、错误类型、修复方式和修复前后哈希。

修复后要重新执行：

```text
Python AST 解析
→ 单条 Test-FP/Test-SP smoke
→ 候选代码注入
→ 测试运行
```

语法错误、测试运行错误和候选代码错误必须分开统计。只有这样，Base/Plus 的最终 Function、Security 和 JointPass 才有可信基础。

### 变体如何理解

PLT 记录包含 `CWE_ID`、`task_description`、`ground_truth`、`rule` 和 `unittest`。它没有显式的 Seed Family 字段，也没有直接标出某三个任务是否来自同一个原始种子。

同一个 CWE 内部存在多种变体。例如 CWE-22 有 70 条记录、41 个函数名和 28 种安全策略，说明它们不是同一个函数的简单复制，而是围绕同一漏洞主题生成的多个任务语义和代码骨架。

因此需要额外构造 family manifest，结合 CWE、任务语义、安全策略、函数签名、漏洞代码骨架和补丁代码骨架生成 family。

### 三个集合如何划分

把 CWE-022 的三个变体分别放入 D_init、D_grow、D_gate，只有在三个变体属于三个不同 Seed Family 时才成立。

如果三个变体属于同一 family，拆开会导致数据泄漏。建议采用：

```text
同一 Seed Family 的所有变体 → 同一个 D 集合
不同 Seed Family 但同一 CWE → 可以分到不同 D 集合
```

这样既可以让三个集合都覆盖 CWE-22，又能保持 family 隔离。

## 3. 让经验形成过程更加可信

### R0 应加入动态验证

当前 R0 主要是 `D_init → 抽取经验 → 语法/静态检查 → M0`。更可信的 R0 应是：

```text
D_init
→ 分析漏洞代码与修复代码
→ 生成安全实现或重建补丁
→ 执行功能测试和安全测试
→ 根据测试结果确认安全经验
→ 通过后进入 M0
```

但 PLT 的动态测试并不完整，部分 `unittest.testcases` 存在语法问题。因此 R0 要记录验证等级：`dynamic_functional_security`、`static_only`、`syntax_only`、`unexecutable_test`。不能把静态门控结果直接表述成完整动态安全验证。

### R1 和 D_gate 的关系

建议在论文和代码中把它们表达成一个“验证驱动经验进化循环”：

```text
检索已有经验
→ 生成代码
→ 动态/静态验证
→ 分析成功差异或失败根因
→ 形成候选经验
→ 质量、有效性、回归门控
→ 晋升、修订或拒绝
```

流程上可以合并，数据上仍必须分开：D_grow 负责产生候选经验，D_gate 负责独立验证候选经验。候选经验不能在生成它的任务上立即自证。

建议增加 `provisional`、`supported`、`narrowed`、`revised`、`demoted` 和 `retired` 状态。如果经验只对特定输入成立，就收窄适用条件；如果后续任务出现安全回归，就降级或退役。

## 4. 用人类学习方式重新解释 SCT

人类学习不安全代码通常包含“规则学习、案例学习、尝试修复、测试反馈和经验修正”。可以映射为：

| 人类学习过程 | 当前 SCT 模块 |
|---|---|
| 阅读安全教材 | D_init 的初始安全经验 |
| 学习漏洞与补丁案例 | 漏洞代码—修复代码对 |
| 根据问题找相似案例 | 检索器 |
| 分析漏洞触发条件 | 经验抽取 |
| 编写修复 | 代码生成器 |
| 测试和代码审查 | 动态测试、静态分析、harness |
| 总结可迁移规律 | 候选经验生成 |
| 专家审核 | D_gate |
| 后续案例纠正理解 | narrow、revise、demote |
| 固化知识 | 冻结库 M* |

经验卡应保存触发条件、安全不变量、推荐动作、危险替代方案、语言实现提示、不适用边界和验证证据，而不是只保存一句“注意路径安全”。

## 5. 如何突出多语言主题

当前代码已经支持 Python、Go 和 C++ 的生成与验证，但 SCT 的经验流程仍主要按单语言处理。需要把经验拆成两层：语言无关的安全语义，以及目标语言的实现适配。

以路径穿越为例：

| 层次 | 示例 |
|---|---|
| 通用原则 | 规范化后的最终路径必须位于可信根目录内 |
| Python | `Path.resolve()` 与 `relative_to()` |
| Go | `filepath.Abs`/`Rel` 与路径逃逸检查 |
| C++ | `weakly_canonical` 与路径组件比较 |

建议增加 Python→Python、Python→Go、Python→C++、语言无关经验→多语言、语言无关经验+目标语言适配等实验。结果按语言、CWE、Base/Plus 和 Function/Security/JointPass 分开统计。

## 6. 检索器是否需要自己训练

当前项目中的检索实现主要在 `methods/legacy_prompt_adapters/run_experiment.py`，`retrieve_cards()` 主要依据 CWE 匹配和词汇重合排序，还不是专门训练的 embedding 检索器。

建议分三步：先用现有词法检索作为基线，再使用预训练的多语言 embedding，最后根据 D_init 的规模决定是否训练轻量检索器。

当前不建议直接训练 embedding 模型，因为 D_init 规模较小，容易记住 CWE 或关键词。检索输入应包含 CWE、任务描述、函数签名、输入来源、敏感操作、目标语言和 harness 约束。

如果后续训练检索器，只能使用 D_init 训练或调参，然后冻结检索器，在 D_grow 和 D_gate 上测试。不能用 D_gate 结果反过来训练检索器。训练目标可以使用“问题—适用经验”为正样本、“相同 CWE 但不同语义”为负样本的对比学习。

## 建议的执行顺序

1. 修复并审计 CodeSecEval Base/Plus Python 测试，保留原始版本和修复记录。
2. 生成 PLT 的 CWE、任务语义、函数名、安全策略和 family 统计表。
3. 构造 Seed Family manifest，按 family 划分 D_init、D_grow、D_gate。
4. 重新定义 R0 的动态验证字段，并区分动态、静态和不可执行结果。
5. 把 R1 和 D_gate 改成验证驱动循环，同时保留数据隔离。
6. 先比较词法检索和预训练多语言 embedding，再决定是否训练检索器。
7. 增加同语言、跨语言和语言适配消融实验。
