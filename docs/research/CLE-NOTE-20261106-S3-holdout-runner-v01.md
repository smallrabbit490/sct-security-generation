# S3开发结果怎样接入留出评价？

**开发择组和H50完整批次入口已接通，25项封网检查通过。** 其中9项检验不同卡库的原生流程，6项检验批次控制，10项检验择组顺序、内容审阅和成本归属。正式M50、H50仍分别为0/500、0/300，没有新增真实模型或Embedding调用。

## 1. 怎样选定进入留出的提炼方式？

先完整完成M50的五条件、两次独立重复及原生回放，再读实际差异代码，核对来源候选。每份来源、重复和提炼条件都要对应真实内容审阅，四种来源方法共400份；空候选、被拒收的卡和正常出卡分别保留。错误判断须引用候选原句及来源材料，不能由字段是否存在自动代签。

G1、G2、G3按既定顺序比较：平均Joint高、相对G0损失少、来源事实错误少、成本低；精确同分按组号。通用规则或原生组仍有验证未测时不择组，完成数不代替完成测量。

前三项已分出胜者时，未知成本保留区间，不影响已经确定的顺序。只有成本确实参与破平时，才检查成本区间能否区分；重叠区间不当作相同成本。原生提炼由G0、G1、G3共享一次返回，按各方法独立执行时需要的调用计入方法成本视图；这些视图不能相加成实际支出。真实支出另按物理请求去重累计，未知用量不当作零，Token不换算成未经核对的金额。

来源单worker的逻辑调用起止时间可以对应实际物理请求，即使两次复审提示完全相同也能核对归属。不能唯一对应的部分保留成本区间。择组记录绑定实际M50记录、原生回放、来源审阅、候选及账本；证据改变后不能沿用旧择组记录。

## 2. 选定后怎样绑定真实卡库？

留出比较G0原生、GW开发胜出组、G4通用指导。GW只是G1/G2/G3的运行标签。两次目标重复使用对应的两次独立来源提炼库。

绑定前以原保存的来源响应重新执行原生归一化和入池，核对待用卡库正文与重建结果一致，再冻结四份真实经验库。相同卡号可以对应不同方法正文，不能沿用另一组的正文或向量。目标生成读取公开题面和实际选中的卡；额外的来源参考实现对象、目标题参考实现和隐藏测试不随输入包直接传给生成模型。

## 3. 完整运行入口是什么？

使用既有项目Python执行`python -B -X utf8 -m configs.cle_weekly_plan_20261105.holdout_stage <动作>`。

1. `prepare`冻结50题、19个近邻组、三条件两重复共300格及本批预算草案，不派发。
2. M50及实际审阅齐全后，`freeze-choice`冻结开发选择；`bind`核对并绑定真实来源库。任一步缺真实证据都保持未就绪。
3. 新预算批准后，`check`核对依赖，`launch`运行。最多四worker，遵守原调用时段；已有CLE进程时不另起重复或冲突实例。
4. 中断后先`audit`、再`probe`。探针用保存响应零API重建到准确缺失请求，未决未核清时不补发。匹配当前输入和完成记录后，`launch-resume`继续，保留旧失败和未知用量。
5. 生成保存齐后自动原生`replay`和`analysis`。已齐时用`finish`只完成回放分析，不再次付费生成。主要得失案例仍由当前Agent实际读代码并记录原因。

择组和来源、方法、输入、卡库均在首次H50结果前冻结。开发或留出收益未过门槛都完成本轮固定范围；预算不足或真实工程故障另行处理，不能把未测写成已测失败。

## 4. 当前还缺什么？

当前检查只剩：开发选择尚未产生、真实卡库尚未绑定、H50新预算尚未批准。来源500次提炼/复审和M50也仍等待对应新预算，尚无真实新结果。

H50预算草案为4500万Token、13000次物理HTTP，其中含4800次Embedding上限；来源提炼和M50费用单列。全部300单元均修复、且每次正常选卡只调用一次时，标准流程共2600次逻辑模型调用。原选卡解析修复规则保持，额外调用继续占用同一有限预算。这是工程支出限额草案，真实来源卡产生后还需核对提示体量，当前不表示预计实付或保证完成用量，也没有新付费批准。
