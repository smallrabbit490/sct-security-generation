# CLE D_gate 全量四臂：原生 P7 与三张上限实验规格

原协议：`cle-q-full-dgate-four-arm-cap3-v1`；当前恢复协议为`cle-q-full-dgate-four-arm-cap3-v4-environment-repaired`，方法参数不变，记录修订与依赖恢复见文末。范围：原恢复三池中的全部 D_gate，298题、217个family、18类CWE。四臂各运行一次，主表共1192条P7；每条最多首次生成加一次修复，主表最多2384个代码版本。用户已要求按CLE实验要求执行，不只是修改选卡上限。

本实验是 A 类固定库开发评价，复用已完成的经验准备/Q学习状态；不是重新执行Phase1/2/3经验演化，也不是Base/Plus最终评测。配置和全298题设计名单位于 `configs/cle_memory_q_full_gate_cap3_20261019/`；实际预检后另存执行清单，不覆盖原始数据。

## 1. Q0–Q3 从哪一次实验后的状态开始

**共同起点为10月18日“全部273题D_grow、不限三张、Q作观察者”的学习结束快照。** 1939卡正文及生命周期与原M0一致，466卡有有效访问（24.03%），有效卡级更新1090次，正Q168卡、负Q298卡。

快照：`translation_work/diagnostics/20261018/cle_memory_q/unlimited_complete_v2/observe/frozen/m_star_q.jsonl`。

| 臂 | 读取哪份卡/数值 | 首次候选顺序 | 谁决定最终入选 | 每次选入上限 |
|---|---|---|---|---:|
| Q0 原CLE | 同一观察学习末快照，Q不参与选卡 | 原向量24+词面8联集顺序 | 原LLM适用性选择 | 3 |
| Q1 相似度 | 同一快照，Q不影响排序 | 相似度降序 | 同一LLM选择 | 3 |
| Q2 学习Q | 同一快照，读取其冻结Q | 原z(sim)/z(Q)融合排序，λ=0.5 | 同一LLM选择 | 3 |
| Q3 打乱Q | 同一快照的只读副本，按同CWE置换(Q,visits) | 置换后按同一公式排序 | 同一LLM选择 | 3 |

Q3只在全实验开始前置换一次，seed=20261015；不按题、尝试或成绩重新打乱。卡正文、状态、数量与语言资格不变，各CWE数值分布保持不变。

Q0/Q1不需要把生产库里的Q清零；它们在选择算法中忽略其影响。所有臂从空代码、无上题反馈开始重新解题，不继承D_grow回测或旧D_gate的代码。

**不用10月16日旧三张学习的297卡/15.32% Q库。** 此次“三张”是评测时的约束，不倒换学习检查点。10月18日273题冻结回测、48题三臂，以及10月19日等K实验、补Q0和160次重复选卡均未更新Q，因此不存在这些实验之后“又进化了一版”的Q。三张上限必要性实验目前仅有设计，也未产出新库。

## 2. 完整复用CLE的哪些要求

执行入口必须调用父运行快照中的 `methods/cle_ablation/runner.py::run_one('PLT', task, 'P7', ...)`，不用另写简化生成器。其余依赖按父run_metadata核对，任何行为变化须另记协议，不能修改旧元数据绕过。

完整前向链为：

`公开契约 → 初析 → 检索 → 经验适用性复析 → 明确采用/拒绝 → 规划 → 完整代码 → 原生动态F/S验证 → Joint早停或一次修复 → 交付末次代码`

- P7保留负向护栏、经验复析和原采用过滤；选卡是中间步骤，不直接把三张卡拼到一个简化生成提示里。
- 四臂均使用`semantic_llm`，`max_experiences=3`；Q1–Q3先对完整共同候选排序，再由LLM最多选三张。不得先截成数值前三张冒充同一方法。
- 数值排序内部应读取完整排序（`rank_candidates(limit=None)`），三张限制由后续原LLM选择协议执行。复析采用ID必须属于已选卡。
- 上限按每次检索/代码尝试计算。c0和c1可选不同卡，整题不同卡合计可能达到6张；不新增“整题累计只能三张”的规则。不强制凑满三张。
- 相同公开题面、完整卡字段、状态/语言资格、原24+8召回、原适用性及英文短编号JSON规则；δ=-1，不另外调门槛。
- 每题新生成一次首次初析，四臂共享。每臂按原召回实现读取共享Embedding缓存，核对首次查询、候选ID与余弦一致；只允许呈现顺序变化。
- 修复轮读取本臂当前代码和原P7许可反馈，按本臂排序/三张规则重新检索、复析、规划、生成。不得读取别臂代码或反馈，不把修复轮当新独立题。
- PLT使用原`validate_and_state`、本地`python -I`与20秒验证预算，不更换验证器，不为本实验引入Docker。
- 首次Joint通过即停止，否则最多一次修复；交付真实末次代码，不按测试成绩回选第一版，不追加生成到通过。

注意现有 `run_memory_q_unlimited.py` 中观察轮标签Q0映射为相似度顺序，不能直接把这个映射复制为本轮原CLE对照。本轮Q0必须传`candidate_order=None`；Q1传`similarity`，Q2/Q3传`q`。

## 3. 固定的模型、源码与公平性

deepseek-v3.2，temperature=0，thinking disabled，每次一般调用max_tokens=4096；原选择器实际输出上限256。向量为text-embedding-3-large。同一批运行、每题四组顺序预先随机轮换、并发最多8；所有组均保留原格式/运输重试并计入用量。

旧48题生成输出不拼入新全量主表，1192条全部按本协议新跑。历史结果只作背景；已有向量缓存可复用。160次重复选卡是不限量协议，证明的是该设置中的选卡影响，不直接证明本轮限三张仍会改选，更不直接证明Joint收益。

公开契约沿用原数据及已存在的公开覆盖，不加入等K实验的新接口提示，不修订return/raise检索白名单，不复制参考补丁、测试输入、答案常量或夹具值。这样仅把候选排序作为四臂差异，避免同时修改模型、提示和卡片组织。若后续决定修订这些内容，另起协议，四臂统一使用，旧成绩保留。

## 4. 先预检全298题，保留真实数据问题

先执行零API原生参考校准、公开依赖及已知契约问题核对，保存每题状态，不由新模型成绩筛题。当前历史预检207题初筛合格，91题未满足；按当时已知坏family标记进一步筛选后仅177题仍满足历史筛选。它们都不是当前“已完整验证的可信题数”。历史参考非Joint46题、占位符46题、未声明依赖54题，类别有重叠。

全298题清单保持不变，包括1015等已知缺陷案例；主表报告计划分母298的已确认Joint通过数，同时单列未测量、技术失败和预检数据问题。**不把缺测当已验证失败，不把数据缺陷全归给Q，也不只跑合格子集后称全量。**

在新成绩产生前锁定“历史/本次预检合格且无已知契约family问题”的诊断子集及理由，辅助报告其同题差异；未彻底澄清的题不冒称可信。完整池成绩只能解释为原评价契约下的结果。验证环境本身无法工作时先停机修复，不能把环境故障转成模型错误。

已知Q开发清单并集覆盖73个D_gate family、104道本池题；其余194题只表示未在这四份Q开发清单中找到暴露，不能称整个CLE从未见过。原D_grow与本D_gate的family无交集。本轮仍是开发池验证，不能替代独立最终测试。

## 5. 执行次序与状态核验

1. 全298题零API预检、冻结输入/Q/实际源码、写定四臂映射及顺序。
2. 预检合格且无已知契约问题的前4题做四臂探针，共16条，计入1192条预算，不按Joint高低换题。
3. 核对完整前向阶段、三张上限、首轮共同查询/候选/余弦、原生F/S、修复与末次交付规则、用量及Q未变。
4. 工程链正确后补齐其余题；已保存失败也不重跑。模型原生解析/采用错误保留并统计，不为了结果好看删题；输入/源码漂移、跨臂数据混用、上限未生效、验证环境故障或认证/额度错误须停止后续调用并记录原因。
5. 全量后复算首版与最终F/S/Joint、救回/损失、题族统计、逐题机制和成本；不按中途成绩调参、扩大重复或重新学习Q。

本轮不以“必须提分”为继续执行条件。探针只确认执行符合协议，不把两题/四题正确当方法有效证明。

## 6. Joint主比较与解释

主要端点是最终交付代码的Joint，不是首次选卡是否不同。四臂主表均给出：计划298、保存行数、完整测量数、F/S/Joint通过数和通过率、流程错误、环境错误、用量。完整测量子集比例另列，不能偷偷替换计划分母。

三个预定主要比较为Q2−Q0、Q2−Q1、Q2−Q3，报告同题救回/损失与净通过数；Holm校正控制三项同时比较的误报。217个family而非298个独立来源：点估计按任务等权，区间按family整簇配对重采样，主推断按family整体交换两臂标签。原项目精确McNemar表保留为补充，不把同family多题当独立证据。

支持“本条件下Q提高Joint”需要Q2相对三个对照均有正向净差、主要校正检验及题族区间支持，并有可核对的选卡—采用—实现路径，且不能由未解决数据/运行缺陷单独解释。只高于Q0但不高于打乱Q，不能证明学习到的数值有独特收益。只有点估计更高则称方向性信号，未显著不称等效或普遍无效。

同时记录限三张后Q是否仍改变首次排序、选入成员与采用成员。无改选/采用时称“本设置干预不足”；已经介入却未提高Joint时，检查共有卡实现、错误适配、公开契约和流程错误，不把“机制介入”写成“方法有效”。四指标和全库召回率本轮不新增标注测量。

## 8. 已观测记录中断与v2修订

v1运行保存29条后，在保存下一条之前触发“轨迹选卡ID与实际传卡ID不一致”断言。最后一批8条已经提交，其中5条已保存、3条没有落盘；不能从断言反造这3条代码、成绩或用量。原29条和源快照保留。

源码核对发现原P7在c1检索抛错时，独立阶段记录会保留当前失败，但顶层retrieval_trace可能仍为c0成功轨迹。v2只修订记录器：先保存原生结果再检查；失败按本次retrieval阶段解释，保留原始轨迹字段；成功检索若确实不匹配、超过三张或共同候选改变仍须停止。离线测试覆盖失败旧轨迹和真实成功不匹配两种情况。尚未落盘的具体3条无法回溯断言原因，不伪称逐条定位完毕。

已完整的6题24条复用，335/1409两个不完整任务全部四组重跑，不按已知成绩挑组补跑。重新使用原298份共享初析（4题原生降级保留），不改变公开契约、卡库、Q、排序、模型、重试或验证器。主表1192条；恢复增加8次P7，全部真实执行总数将为1200，旧5条排除记录的已知用量另计，旧3条未知用量明确缺失。

执行器在同一预定题内随机顺序下持续保持至多8个P7任务，去除等待整批最慢任务的屏障；这是调度修订，不按结果决定下一题，不改变并发上限和P7内部过程。恢复探针为上述两题共8条，纳入主表。入口`methods.cle_ablation.run_memory_q_full_gate_v2`，详细修订为`configs/cle_memory_q_full_gate_cap3_20261019/protocol.v2.json`。

## 9. U+2028读取问题与v3持久化修订

v2到80条时，原`read_rows`使用`str.splitlines()`，把第103题Q1代码字符串中的4个U+2028字符当作JSONL记录边界而汇总中断。逐物理行解析确认80条JSON均有效，不删除字符或修改代码。此前监看错误被初步解释为读到半行，该解释已更正；实际是上述确定的分行缺陷。

中断时主汇总尚未消费的7个已提交任务没有落盘，涉及1267四组和338三组。v3复用20题全部四组共80条；1267/338两题四组整批恢复，338另一组本来尚未提交。因此第二次额外重复7次，加上第一次8次，预计真实总执行1207次P7；主表仍1192条。旧5条排除记录计入已知用量，3+7条旧结果的调用/Token未知，已知费用统计为下界。

v3只按物理文件行读取JSONL；工作线程内先原子保存每条原生记录，再交主线程汇总。即使主汇总报错，已完成结果可由`task_rows/<id>/<arm>.json`无API恢复，不再依赖尚未消费的Future。六项离线验证覆盖四臂映射、原P7与三张、真实成功轨迹不匹配仍停止、失败检索旧轨迹、U+2028，以及独立结果恢复。方法参数、题目、验证器、Q和原结果保持不变；当前入口`methods.cle_ablation.run_memory_q_full_gate_v3`。

## 10. 原镜像PyYAML依赖恢复与v4协议

经uv dry-run确认后，仅在原CLE虚拟环境安装官方PyPI二进制轮子`PyYAML==6.0.3`；未改验证器或数据。全D_gate夹具与参考导入清单检查未发现其他缺失。随后零API重验全部280个已存代码尝试和298题参考，只有1402的原许可反馈改变。原174题预先诊断名单保持不变，不按新成绩调换分母。
