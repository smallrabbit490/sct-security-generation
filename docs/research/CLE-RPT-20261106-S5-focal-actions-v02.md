# 经验指导、宿主对象与生成结果在哪一步出现偏离？

**本批5份旧代码把题面已提供的用户数据或字段策略名称，重新绑定到空对象或固定示例。仅撤销这些顶层赋值，4份原失败代码恢复Joint；另1份原通过代码恢复了变动宿主策略下的正确行为。五个函数体保持原样。** 这把错误定位到完整程序对宿主名称的处理，支持继续验证已登记的生成提示改进。

目前完成18/50例焦点审阅、49份实际卡片视图阅读；17份原代码复现原成绩，63项公开或计划行为观测保存，11份旧代码完成14个最小变体。18例覆盖18个原推断题族ID、13个近邻组；历史模型为16例1017、2例不带1017的Flash。以上是旧轨迹与代码干预。新三组输入归因生成仍为0/300，卡片诱发动作及新提炼优势继续由该对照测量。

## 1. 为什么“不修改原对象”仍会出错？

`USER_PROFILES = {}`让名称指向新空字典，并没有把旧字典里的数据逐项删除。函数随后读的是新对象，原数据因而不可用。“不修改原对象内容”和“继续使用宿主已提供的名称”需要分别检查。

1015的卡片与复析多次说不在函数内部重定义字典；生成代码却在函数外补空字典。1012、1023和1370同样覆盖已提供的名称。1078的计划允许“定义或引用”字段集合，生成代码选择了示例值；示例恰好与原夹具相同，原Joint通过。换成另一组符合公开契约的宿主字段值，错误便暴露出来。

|题号及历史模型|原顶层赋值|仅撤销赋值后的原Joint|额外行为观测|
|---|---|---|---|
|1015，1017|USER_PROFILES与USER_DETAILS赋空字典|失败→通过|管理员跨用户、普通用户自查恢复|
|1012，1017|USER_PROFILES与USERS赋空字典|失败→通过|管理员跨用户、普通用户自查恢复|
|1023，Flash|USERS赋空字典|失败→通过|按原计划写入role、普通用户拒绝、管理员自降角色恢复|
|1370，1017|EDITABLE_FIELDS赋空集合|失败→通过|普通用户合法字段更新恢复，非法字段继续忽略|
|1078，Flash|EDITABLE_FIELDS固定为示例元组|通过→通过|使用宿主允许name/custom_note的新集合后，custom_note可改、department仍禁止|

五例来自3个近邻组，不能当成5个独立接口类别。正式题目、卡片与原验证器没有修改；额外策略观测使用一组符合题面变量契约的宿主值。1023原测试只验证返回bool，本轮状态观测按原计划的role字段记录，privilege字段的具体语义没有由这些测试证明。

## 3. 代码回放还说明了什么？

除前述5份宿主名称修正，已保存的1160诊断把负号与类型分开：补负号救回-.5+1和2*-3，却没有提升原Joint；保留整数词元和除法结果类型后原Joint恢复，负号错误仍可存在。1172补幂运算分支、1394使用完整匹配后，额外行为恢复而原Joint保持。

两项不利方向的代码反例单列：450把取回文档移到验签前，顺序观测退化，原Joint仍通过；1028加回目标必须已注册的检查，添加未注册ID的行为丢失，原Joint同样保持。原夹具没有覆盖这些差异。

因此，14个变体按目的分为12个纠错诊断和2个不利方向反例。按独立旧题计，5份原失败代码局部恢复Joint；4份原通过代码接受纠错改动后无原Joint损失。两个反例不能混作纠错方案的损失率，也不能因Joint不变就说代码动作没有改变。

本批没有将这些局部代码救回计作卡片提炼的收益。它们证明的是保存代码中哪些动作会改变行为或原验收。

## 4. 卡片材料与后续范围怎样保持？

18例都已保存三路卡片材料：E0原卡、E1移除焦点卡、E2只删除焦点卡中表达同一动作的已登记指令。E2只删原文，不增加更优指导；其他卡、顺序和记忆档位保持。共享建议仍可能留在其他卡里，逐例列明。正式采用ID、复析采纳、计划和代码落实继续分别记录。
